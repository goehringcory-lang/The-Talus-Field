# API Worker (`workers/`)

Guidance for the API Worker at `api.thetalusfieldjournal.com`. Loaded when working with files under `workers/`.
Repo-wide conventions, the editorial site, and the deployment model live in the root `CLAUDE.md`.

## Worker architecture

Routes mounted in `workers/src/index.ts`:

- `/api/auth/login` — email + 6-digit code path, KV-backed buyer lookup. This is the real buyer sign-in: the PWA's `Login.tsx` tries it first and falls back to `/api/auth/dev-login` only on 401/429.
- `/api/auth/dev-login` — **active** username + code path, env-backed (`DEV_USERNAME`/`DEV_CODE`/`ADMIN_USERNAME`/`ADMIN_CODE`). Pre-Stripe; either pair issues a JWT.
- `/api/auth/exchange` — exchanges a magic-link `accessToken` for a JWT. The `token:<hex>` reverse index has no TTL, so `putBuyer` deletes the prior token's entry whenever a re-provision (lapsed re-purchase, new promo trial) derives a new token; otherwise a superseded magic link kept unlocking the new access window.
- `/api/checkout/*` — Stripe Checkout session start + inventory cap enforcement, plus `/claim`, the instant-access exchange (August 2026): a plain purchase's success URL carries `session_id={CHECKOUT_SESSION_ID}` back through the editorial `/guide` page (which fires the GA4 purchase event, then forwards) into the PWA's `/claim` page, which POSTs the id here. The route verifies the session against Stripe directly (`retrieveCheckoutSession`) rather than waiting for the webhook, because the redirect usually beats the event, then signs the buyer in: an active buyer record answers as-is, a missing/lapsed one is provisioned on the spot. Provisioning is race-safe by construction — `lib/provision.ts` derives `accessToken`/`accessCode` from the session id (HMAC, `MAGIC_LINK_SIGNING_SECRET`) and stamps `provisionedSessionId`, so the claim and the webhook writing the same purchase concurrently produce byte-identical records, and the webhook skips its 18-month extension when `provisionedSessionId` matches the session (a repeat purchase by an active buyer still extends, keyed per event id as before). The claim never sends email and never touches inventory: both stay webhook-owned. Gift and renewal sessions 409 (the recipient is not at the payer's browser; renewals already land signed in). Rate-limited per hashed IP; unknown session and wrong product answer the same 404 so the endpoint can't probe what else the Stripe account sells; a session whose record the refund webhook already revoked answers 409, because Stripe leaves a refunded session at `payment_status: 'paid'` and the id sits in the buyer's browser history. The editorial `/guide` page still calls `/api/inventory` for the scarcity counter (which also returns `priceCents` and `renewalPriceCents`). `/start` accepts an optional gift body (`{gift, recipientEmail, giftNote}` → session `metadata.kind = 'gift'`; the webhook provisions the **recipient** and mails the payer a receipt). `/renew` starts a discounted renewal (`GUIDE_RENEWAL_PRICE_CENTS`): `POST` is JWT-gated for the PWA Account button, `GET ?token=<accessToken>` serves the emailed notices (rate-limited, 302 to Stripe); renewals bypass the monthly cap, extend `expiresAt` from max(now, current), and keep the buyer's token + code. A daily cron sweep (`lib/renewals.ts`) sends T-60/T-14/T-1 renewal notices, deduped per (email, stage) by KV sentinels.
- `/widget/conditions` + `/widget.js` — the free embeddable conditions box for gateway-business sites (live entrance waits proxied from the NPS S3 feed via `lib/waits.ts`, KV-cached 5 min, + a 3-day Valley fold of `weather:v1`). Mounted at the **root** level like `/tiles`, NOT under `/api/*`, because the API CORS middleware echoes allow-listed origins and embeds need `*`. The editorial `/widget` page is the pitch + snippet + live preview (its preview is why `api.thetalusfieldjournal.com` is in the CSP `script-src`).
- `/api/stripe/webhook` — Stripe webhook handler for `checkout.session.completed` (provisions a buyer record in KV — `expiresAt` = purchase + 548 days, a true 18 calendar months — and emails the access code; when `/api/checkout/claim` already provisioned the same session it keeps that record untouched and still owns the email + inventory) and `charge.refunded` (any refund, full or partial, revokes access by setting `expiresAt` and `refundedAt` to now; missing email or unknown buyer is logged for manual revoke, not failed). Idempotent via a `stripe_event:<id>` dedupe key. Sessions completed with `payment_status: 'unpaid'` (async payment methods) defer provisioning to `checkout.session.async_payment_succeeded`. All three events must be enabled on the Stripe webhook endpoint — see the DEPLOY.md launch checklist.
- `/api/redeem` — **unauthenticated** shared promo-code redemption (`routes/redeem.ts`; the PWA's `/redeem` page posts here). Codes live in `PROMO_CODES` in wrangler.toml (`"CODE:DAYS"` comma-separated; `TALUS30:30` is the standing 30-day newsletter code — edit + `wrangler deploy` to add or retire one). POST `{email, code, website}` (`website` is a honeypot): a valid code provisions a **normal buyer record** for DAYS days with `promoCode` set and emails the magic link + 6-digit code via `sendTrialAccess`, so login/expiry/sync need no promo awareness. One grant per (code, email) ever (KV sentinel, claimed only after the email sends); an ACTIVE record is never clobbered — the redeemer gets their existing access email re-sent instead, which also keeps the endpoint from confirming who bought the guide. No inventory increment. Rate-limited per email (3/hr) and hashed IP (10/hr). The renewal sweep skips the t60 notice for `promoCode` records (a 30-day grant would get "ends in two months" on day one) but keeps t14/t1 as the trial's conversion notices; any real payment clears `promoCode` (stripe.ts) and restores the full ladder.
- `/api/contact` — editorial contact form backend (`page-newsletter-contact.jsx` posts here). Validates a fixed subject enum, uses a `website` honeypot field against bots, and relays via Resend (`lib/email.ts`).
- `/api/indexnow/submit` — bearer-token-gated POST that forwards a `{ urls: [...] }` list to api.indexnow.org. Push-indexes Bing / Yandex / Seznam / Naver / Yep in a single call. Use `scripts/indexnow-ping.sh` after publishing an article. Requires `INDEXNOW_KEY` and `INDEXNOW_ADMIN_TOKEN` secrets.
- `/api/programs?start=&end=` — **unauthenticated** merged park-program listings for a trip window (≤31 days): NPS Events API data from the `GUIDE_PROGRAMS` KV cache plus the hand-curated `src/data/manual-programs.ts` (Conservancy / Aramark / astronomy — the NPS API doesn't carry most partner events). The overnight cron (`[triggers]` in wrangler.toml, `scheduled` export in `index.ts`) ingests a rolling 120-day window; the route self-heals with a live fetch + KV backfill when the cache is missing or >48h old (the backfill is single-flighted per isolate so a stale-cache thundering herd can't burn the NPS hourly quota). Needs the `NPS_API_KEY` secret (free, developer.nps.gov); without it the feed serves manual curation only. Seasonal curation workflow: edit `manual-programs.ts` (zod-validated at load), `wrangler deploy`. **Most manual entries are windowed to the current Yosemite Guide edition (`GUIDE_START`/`GUIDE_END` at the top of the file) and need a re-curation pass each ~5 weeks when the new edition posts**, same cadence as the editorial `bulletin.json` — and that pass must re-read the Programs page's **symbols** as well as its rows: `accessible` and `familyFriendly` are the printed wheelchair and Recommended-for-Families marks, true-only (an unmarked program is unmarked, not excluded), and they are the only program fields the NPS feed cannot supply. Two different programs may never share a date and a title: the route's dedupe key is exactly date + normalized title, so one NPS entry matching it drops every manual entry behind it — the guide prints several programs under one name (Campfire Program, Jr. Ranger Discovery Table), and those carry location-qualified titles. A load-time guard at the bottom of `manual-programs.ts` fails the deploy on a new collision between entries in different places, while still allowing two showings of one program at one place (the noon and 3 pm Welcome to Tuolumne! talks).
- `/api/trip/plan` — the PWA's cross-device sync (`routes/trip.ts`). GET/POST/DELETE, all JWT-gated, KV keyed by sub, 60 writes/hour, 256 KiB cap. Whole-document last-write-wins on the client's `updatedAt`, and the POST **enforces it server-side**: a write whose stamp is older than the stored record's 409s (equal stamps pass, so re-pushes stay idempotent) — without that, a GET→POST race or a skewed-back client clock silently destroyed the newer device's plan. **The Worker never parses the document**: the trip schema lives in `apps/guide/src/trip/schema.ts` and evolves with the app, so a server-side mirror would mean a Worker deploy per planner change and a stale mirror would start rejecting valid plans. The Worker owns the envelope, the size, the write rate, and the stamp ordering; the PWA re-validates on read (`apps/guide/src/sync/schema.ts`, salvage-on-partial-corruption). Opt-in and off by default.
- `/api/push/*` — web push for the PWA (`routes/push.ts`, `lib/push.ts`, `lib/pushSweep.ts`). `GET /key` serves the public VAPID key, `POST /subscribe` and `DELETE /subscribe` are JWT-gated device registration, and `POST /pending` is **unauthenticated on purpose**: it is called from the service worker's push handler, which has no access to localStorage and therefore no token, and the 100+ character push endpoint it presents is already the capability that lets anyone push to that device. Pushes are **payload-less** — RFC 8291 payload encryption is the riskiest code this Worker could hand-roll and fails as "notifications silently stop", so the woken SW asks what the push was about instead. VAPID ES256 signing IS implemented (WebCrypto emits raw r||s, exactly what JWS wants). Needs `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` secrets (`node scripts/gen-vapid-keys.mjs`); without them every route 503s and the app hides the opt-in. `sweepPush` sent exactly two notices until September 2026 (a morning-of nudge on each trip day, and renewal heads-ups at T-14/T-1); the road and deadline notices under `/api/parking` below make four, and the campsite opening under `/api/watch/*` below is the fifth. **It runs on its own morning cron (`0 15 * * *`, 7-8am Pacific year round) and is additionally gated on the 6-11am park-time window** — the overnight data cron (10:00 UTC = 2-3am Pacific) used to be the only trigger, which made the trip-day nudge unreachable and would have buzzed renewal notices at 3am. A device's most urgent un-sent notice wins (renewal over trip day), and a notice already sent falls through to the next candidate instead of silencing the device. Trip dates are the one piece of planner state that reaches the server outside the opaque sync doc, because a morning nudge cannot be scheduled without them.
- `/api/watch/*` — campsite watches for the PWA's Openings tab (`routes/watch.ts`, `data/campgrounds.ts`, `lib/recreationGov.ts`, `lib/availabilityMatch.ts`, `lib/availabilitySweep.ts`; September 2026). `GET /targets` is the public registry, the thirteen reservable campgrounds with their recreation.gov ids, hand-mirrored in `apps/guide/src/watch/targets.ts` and held in step by `scripts/check-watch-targets.mjs`; `GET /`, `POST /`, `GET /:id`, `POST /:id` (channels; CORS allows no PATCH) and `DELETE /:id` are JWT-gated. A watch is `watch:<sub>:<id>` in `GUIDE_BUYERS` with an absolute expiration three days past its last night: cap five per buyer, 1 to 14 nights, first night up to 190 days out so unreleased (NYR) nights can be watched for release day, 30 writes an hour per sub, and an identical re-POST answers 200 with the existing watch. **The `*/5 * * * *` cron runs `sweepAvailability`**: fetch each recreation.gov (campground, month) grid that at least one live watch needs (`GET www.recreation.gov/api/camps/availability/campground/<rgId>/month`, an identifying User-Agent, a 10 s timeout, `Available` the only status kept, compacted to `avail:rg:<rgId>:<yyyy-mm>` in `GUIDE_PROGRAMS` with a 6 h TTL), evaluate every watch with the pure matcher (`any` = one wanted night open on any site; `full` = one site open on every wanted night; Camp 4 is per-person `quantities` against `party`), and alert on a **transition only**, a night open now that was not in `lastOpen`, with a ten-minute per-watch backstop for the cart-release flapping recreation.gov shows after a release; a night nobody was told about (backstop, run cap, no device) stays out of `lastOpen` so the next run that can tell them does. Push goes to every device of the sub (`Urgency: high`, a 1 h TTL, sentinel `watch-<id>-<fingerprint>` with a 1 h TTL) and email to the sub when it is an address with a buyer record; refunded and lapsed buyers have their watch deleted unalerted. **Not morning-gated, on purpose**: the one exception to the push sweep's rule, because a site released at 7:00 a.m. is gone by 7:02 and the buyer asked per watch. The steady state writes nothing (a record is rewritten only when its state changed; "last checked" is the grid's `fetchedAt` and the view's `open` is the grid's current answer, both read by the routes; `lastOpen` is what the buyer has been told), an idle run is one KV list, and the device index is built lazily on the first alert. An unhealthy answer (403 / 429 / 5xx / timeout) backs the whole sweep off, 5 to 60 minutes via `avail:backoff:rg`, and stamps `lastError` on every watch so the buyer sees why. Known and accepted: `pushPending:<hash>` is one slot, so an opening and the morning nudge queued for one device inside the same hour leave the later notice standing. Needs the Workers Paid plan's CPU budget (500 KB grids every five minutes). Scenario 23 in `test/e2e-flow.mts` drives the sweep in-process against synthetic grids.
- `/api/trip/email` — **unauthenticated** editorial trip-link mailer (`routes/trip-email.ts`; mounted before `/api/trip` on purpose). POST `{email, stops, website}` from the editorial map's TripEmailBox; `website` is a honeypot (non-empty → fake 200). Validates and dedupes stop ids (≤30, `[a-z0-9-]`), builds the `/map?trip=…` URL server-side (so it can't mail arbitrary links), sends via Resend (`sendTripLink` in `lib/email.ts`), and rate-limits to 5 sends/hour per SHA-256-hashed IP in `GUIDE_BUYERS` KV.
- `/api/weather` — **unauthenticated** NWS forecast proxy (`routes/weather.ts`, `lib/weather.ts`). No params; returns all four fixed park spots (ids match the PWA Region enum). Two-step api.weather.gov fetch (points → gridpoint forecast), keyless (User-Agent required, no secret). Cached in `GUIDE_PROGRAMS` KV (`weather:v1`, plus a gridpoint-URL cache); the route refreshes inline when the record is missing or >2 h old and a failed spot keeps its stale copy; responses carry `max-age=900`. The daily cron also calls `refreshWeather` as a floor. The zod schema is hand-mirrored in `apps/guide/src/weather/schema.ts`.
- `/api/waits` — **unauthenticated** live entrance waits for the PWA (`routes/waits.ts`). Serves the same display shape as the widget via the shared `waitsDisplay` in `lib/waits.ts` (KV-cached 5 min by `getWaits`; stale or missing entrance → `minutes: null`); a dead feed serves `{fetchedAt: null, waits: []}`, never an error. Mounted under `/api/*` on purpose (unlike `/widget`): the PWA's `apiFetch` sends preflighted headers, which the origin-echo CORS middleware answers.
- `/api/parking` — **unauthenticated** live lot status (`routes/parking.ts`, `lib/parking.ts`), the waits route copied: NPS API `parkinglots` for `yose`, KV `parking:v1` cached 5 min, stale-on-failure, dead feed serves `{fetchedAt: null, lots: []}`. The one rule is that `liveStatus` is mapped honestly: a blank occupancy is `unknown` and consumers hide it; only a word the park wrote (Light/Moderate/Heavy, Full, Closed) becomes a status, and the raw word rides as `statusText`. Falls back to NPS's shared `DEMO_KEY` when `NPS_API_KEY` is unset, which is fine for a preview and not for a July Saturday. **The road watch (`lib/roads.ts`)** runs after the nightly `refreshAlerts` on the record it returns: it derives closed/chains/open/unknown for seven roads (the four park roads plus 120, 140 and 41 by highway number or in-park name), keeps `roads:watch:v1` in `GUIDE_PROGRAMS`, and acts on a change only after two consecutive refreshes agree (a candidate that reverts is discarded; a failed refresh cannot count as the second reading, so a change is announced about a day late by design). Acting means one plain email to the contact inbox (`sendRoadChangeNotice`) and a change record the push sweep reads; nothing is ever sent to the newsletter by the Worker, the owner sends the `alert-tioga` / `alert-roads` email by hand. **`sweepPush` sends four notices now**: `road-<id>-<date>` for devices whose trip window touches the next 14 days (changes fresher than 2 days only), and `deadline-<id>-<date>` the morning before a deadline the device opted into (`deadlines` on the push record, validated against `lib/deadlines.ts`, which imports `scripts/data/deadlines.json` at build time so a row edit ships with the next deploy). Order is renewal, road, trip day, deadline; the dedupe-by-(device, stage) sentinel is unchanged.
- `/api/inventory` also returns `priceCents` (from `GUIDE_PRICE_CENTS` in wrangler.toml) — the editorial buy box renders it live, so the price is edited in exactly one place.

Both auth paths sign the same JWT shape (`{ sub, iat, exp }`, HS256, 90-day TTL) using `MAGIC_LINK_SIGNING_SECRET`. The `sub` claim carries an email for `/login` and a username for `/dev-login` — the PWA doesn't care which.

CORS in `index.ts` allow-lists the editorial origin, the PWA origin, and `http://localhost:5173`/`5174`/`8000` for local dev. Add new dev origins there.
