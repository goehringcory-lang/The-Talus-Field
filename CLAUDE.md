# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project shape

This repo contains three subsystems for **The Talus Field**, a Yosemite editorial site and field guide product. They are intentionally co-located so a single change (e.g. brand rename, copy update) can touch all three at once.

| Path | What it is | Stack |
|---|---|---|
| repo root (`*.jsx`, `index.html`, `styles.css`, `bodies/`, `img/`) | **Editorial site** at `thetalusfieldjournal.com`: articles, interactive trip-planner map (`/map`), film archive (`/films`), packing checklists. Static, no bundler. | Vanilla React: `*.jsx` sources precompiled into `/dist/*.js` by `scripts/gen-compiled.mjs` (`index.html` loads the dist files); styled with hand-written CSS in `styles.css`. Edge SEO via the root Worker entry `edge/seo.js` (see `wrangler.jsonc`); response headers/CSP in `_headers`. |
| `apps/guide/` | **Field Guide PWA** at `guide.thetalusfieldjournal.com` (custom domain attached at launch; the `talus-field-guide.pages.dev` host keeps resolving alongside it for magic links already sent). Account-gated **paid product** ($3.99 one-time, 18-month access; see "paid model" below), offline-capable. | Vite + React 19 + TypeScript + react-router-dom + zod. |
| `workers/` | **API** at `api.thetalusfieldjournal.com`. Auth, Stripe checkout/webhook, KV-backed buyer records, contact form, IndexNow, NPS programs feed (`/api/programs` + daily cron), live park feeds (`/api/weather`, `/api/waits`, `/api/parking`, `/api/alerts` with the nightly road watch, `/api/air`, `/api/flow`), trip-link email (`/api/trip/email`), PWA trip sync and web push, the remote photo upload (`/photos`). | Cloudflare Worker + Hono + `@tsndr/cloudflare-worker-jwt` + KV. |

Each subsystem carries its own memory file, loaded when you work under it: `apps/guide/CLAUDE.md` (PWA architecture) and `workers/CLAUDE.md` (API routes and auth).

**`ROUTINES.md` is the owner's manual for the scheduled agent fleet** (sixteen Routines as of September 2026: the two weekly articles and the monthly edition, the evergreen refresh, the bulletin turn, the intel cycle and executor, the revenue pulse, the Field Guide depth pass, the Sunday letter draft, the site sweep, and, added September 23, the Field Guide fact audit, the reference page refresh, the season pre-flight, the dependency and security check, and the daily road alert drafter). Each has a runbook under `.claude/skills/<name>/SKILL.md`, and the territory table in ROUTINES.md decides which routine may touch which file; a new routine gets a row there before it gets a cron. The same file records the environment's network access (full Internet since September 2026) and the hosts the runbooks reach.

DEPLOY.md has a full deployment runbook (its "2026 relaunch: enabling the $3.99 paid model" section is the 8-step go-live sequence). It matches the region-based PWA (`valley`/`glacier-mariposa`/`tuolumne`/`hetch-hetchy`, 66 stops, 44 core and 22 hidden, as of September 2026) since the July 2026 launch-prep refresh; if a step contradicts the code, trust the code and fix the doc. `CONVERSION-STRATEGY.md` (July 2026) is the current reader→subscriber→buyer growth plan, successor to `GROWTH-AUDIT.md`. `FEATURE-RESEARCH-2026-09.md` (September 2026) is the cross-product feature determination: five ranked changes for the site and the PWA with market evidence, the price decision that precedes them, and the ideas set aside; its PWA-only companion is `apps/guide/PWA-FEATURE-RESEARCH-2026-09.md`.

## Common commands

Local dev: `.claude/launch.json` has the site + PWA configs; the Worker is `cd workers && npm run dev`.
Tooling scripts live in `scripts/package.json` (`npm --prefix scripts run <script>`); `npm --prefix scripts run check` is the pre-commit gate and `run checks` is the offline health battery.

Dev tooling lives in `scripts/` with its own `package.json`, deliberately not at the repo root, so the root stays a static, build-free deploy. Run `cd scripts && npm install` once before using the npm scripts above. The root `package.json` is NOT a tooling home: it exists only because the Cloudflare Workers Build for the editorial worker runs `npm run build` before deploying, and its `build` script is a no-op echo. Do not add dependencies or real build steps to it (`.assetsignore` also excludes it from the asset upload).

Deployment is **not** done from this repo's CI. On merge to `main`: the **editorial site** deploys via a git-connected Cloudflare **Workers Build** (root `wrangler.jsonc`; it runs the root `npm run build` shim then `npx wrangler deploy`, uploading the repo root as static assets with `edge/seo.js` as the Worker entry); the **PWA** deploys via the git-connected Cloudflare **Pages** project `talus-field-guide` (root dir `apps/guide`, build `npm run build`, output `dist`, Node pinned by `apps/guide/.nvmrc`). The **API Worker** has deployed the same way since September 2026, through its own git-connected **Workers Build** on `talus-field-guide-api` (root dir `workers`, build `npm ci && npm run typecheck && npm run test:flow && npm run test:roads`, deploy `npx wrangler deploy -c wrangler.toml`; the full settings table is in DEPLOY.md section 4). Before that it shipped only by a manual `wrangler deploy`, so an older issue, brief or PR body asking the owner for one describes the retired model. Its settings live in the dashboard, not the repo, and four of them are load-bearing. (1) **Merging an `[api]` PR ships checkout, the Stripe webhook and the buyer records**, and `main` is not branch-protected, so CI's red Worker job does not stop a merge. (2) That is why **the build command is the gate**: the same typecheck and test suites run before `wrangler deploy`, and a failure ships nothing and leaves the previous version serving, so the only signs are the build log on the Worker's Deployments tab and the nightly `checks/api.mjs` parity error. (3) **Build watch paths** are `workers/*` and `scripts/data/deadlines.json` (the Worker imports it at build time), so an article merge does not redeploy the API; a new build-time import from outside `workers/` needs its path added there, or its edits will not ship. (4) **Preview builds are off**: this Worker holds the live Stripe key and the buyer records, and a branch's code has no business running beside them before review. An unattended build never sees wrangler's config-drift prompt (it applies `wrangler.toml` as written), which is one more reason the `[[routes]]` custom-domain block must never leave that file. Secrets are still set by hand (`wrangler secret put`) and survive every deploy. A manual deploy is the recovery path, and it runs from a clean worktree of `origin/main`, never a feature branch: wrangler uploads whatever is on disk, so a branch behind `main` rolls production back.

## Editorial site conventions

- **No bundler, but a compile step.** The `*.jsx` files at the root are the source of truth, but the browser loads the precompiled `/dist/*.js` versions (no in-browser Babel). After editing any root or `bodies/` jsx, run `npm --prefix scripts run compile` and commit the regenerated `dist/` files alongside the source; `npm --prefix scripts run check` fails if they drift. Edge SEO head rewriting is done by `edge/seo.js`, the root Worker's fetch handler (ported from the retired Pages Function `functions/_middleware.js`); it also injects crawler prose for hub routes (`HUB_PROSE`) and serves unknown paths as real 404s.
- **Static homepage shell (July 2026 LCP pass, part two).** `/` ships its above-the-fold markup, the homepage masthead plus the hero, as plain HTML inside `index.html`, between the `GENERATED:HOME-SHELL` markers, so it paints on the first byte instead of waiting on the SPA boot. `scripts/gen-home-shell.mjs` (`npm --prefix scripts run home-shell`, guarded by `run check`) renders it from the **real** `Header` (called with `current: "home"`, so since September 2026 what it bakes is `HomeMasthead`, see the homepage bullet) and `HomeHero` components, so it cannot drift from what React draws a moment later; React replaces it on boot and `app.jsx` removes any leftover `#home-shell`. Three rules: (1) `HomeHero` must render without browser APIs on its first pass, since the generator has no DOM; (2) nothing date-derived may be baked in. The September 2026 hero and masthead carry no dated copy at all, so `DATE_SLOTS` is an empty table, but the mechanism stays: a future dated slot in `HomeHero` or `HomeMasthead` is registered there so the generator blanks it to a stable-height placeholder for React to fill, and the visible-text guard (a four-digit year or the current month name) still fails the build on a leak; (3) `/` is served straight off the asset layer and never invokes the Worker (see `wrangler.jsonc`), which is why the shell lives in `index.html` and `edge/seo.js` *strips* it on every other route. The sr-only `#seo-static-h1` moved out of `index.html` into the Worker for the same reason: the homepage has a real `<h1>`. `MUST_CONTAIN` asserts the h1, the intro, the three section links, the homepage masthead, its search box and its Park now menu survived a refactor; edit that list when the hero's copy changes.
- **The design system, site-wide (September 2026 rollout, `DESIGN-ROLLOUT.md`).** Every route on the editorial site, plus the generated `/archive/` pages, renders in the homepage's system; the page inventory and its status live in `DESIGN-ROLLOUT.md`. Seven things are load-bearing. (1) **One base layout**: app.jsx renders `<Header>` (`HomeMasthead`), then `<main class="hp-design">`, then `<Footer>`, so every page inherits the tokens, the type and the `:where(.hp-design)` element base from `<main>`; the static home shell's `<main>` carries the same class. (2) **One palette**: the design palette (cream paper, deep green ink, rust accent) is the only one, defined at `:root` both as the site tokens (`--paper`, `--ink`, `--moss`, ...) and as the system's own `--hp-*` names. The Golden Hour / Granite / High Sierra swaps, the density swap, the Tweaks panel (`tweaks-panel.jsx`) and every `prefers-color-scheme` block are gone, so **the site renders light in dark mode**; a dark scheme would be a new design pass, not a restore. (3) **Pages are built from the `Hp*` components**: `HpPageHead` (crumbs, eyebrow, h1, intro, actions, byline, an optional aside, `children` under the byline, `as` for a `<header>`), `HpHeading`, `HpRow`, `HpCard` / `HpArticleCard`, `HpGuideBand` (one per page), `HpLetter` (it passes `variant` through, and `children` render between its h2 and the form, which is how `/dates` carries its reminder chips) and `HpPostcard`. Prose pages use the reading column (`.hp-wrap.hp-reading > .hp-reading__column`, 680px), and a page ends in the homepage's order: guide band, then letter. Each page has one layer at the end of `styles.css`, named after the page (`.hp-index`, `.hp-stay`, ...); **check a new layer name against the homepage's own classes first** (`.hp-articles` is the homepage's featured grid, which is how the first `/articles` build became a two-column grid). (4) **The shared legacy primitives are rewritten in place in the design's language, not overridden**: `.prose` (also the prerendered fragment's `#prerender-prose`), `.placeholder`, `.btn`, `.eyebrow`, `.crumbs`, `.chip`, `.field`, `.nlbox`, `.toc`, `.statblock`, `.relrail`, `.places-pitch`. Prose links and prose `h3` metrics sit at **zero specificity** (`:where(.prose:not(.guide-prose))`), so a component's own class inside a prose block still wins; a rule like `.prose a { ... }` would override `.lodging-cta__link`. `/guide`'s sales copy keeps its pre-rollout reading block through `.guide-prose` restatements placed right after `.prose`, and `LodgingCta` keeps the look PR #413 accepted on `/planning`. (5) **The footer and KeepGoing are in the palette and on the homepage's container** (the post-rollout review pass): they used to pin the retired High Sierra near-black (`#11161c`, `#0c1014`) and sit on the legacy `.wrap`, so their left edge never lined up with the page. Both now restate `.hp-wrap`'s box on their `.wrap`; a change to `.hp-wrap`'s widths or breakpoints has to be mirrored in that rule in `styles.css`. (6) **The masthead's slot is not sticky and its height varies with width** (132px desktop, 173px at phone width; from 761px to 879px the nav takes its own row, as on phones, so its labels never wrap), so `/map` measures it (`useMastheadHeight` in page-map.jsx sets `--masthead-h`) instead of hard-coding a height. Past the slot the header becomes the compact bar (Navigation bullet), which is off on `/map`, so that measurement is unchanged. (7) **The archive's chrome is a hand-kept mirror** in `gen-archive.mjs`: `DESIGN_NAV` (HOME_NAV's four labels, each linked to its group's landing page, since the archive loads no JavaScript and the menus cannot open; the search box as a plain GET form to `/search`; no compact bar) and `siteFooter()` (Footer's columns, the section list read from the catalog, and no copyright year, which would fail `--check` every January 1). Change them with `HOME_NAV` and `Footer`, bump `ARCHIVE_CONTENT_UPDATED`, and run `run archive`. To add or rebuild a page: build it from the `Hp*` components (keep every link, ask, tag and tracking location), add a page layer, then run the pixel diff of `/`, `/planning`, `/conditions` and `/guide` before and after.
- **Route-level lazy loading (July 2026 LCP pass).** `index.html` eagerly loads only the shared shell: the self-hosted React UMD files under `/vendor`, `storage.js`, `affiliate.js`, `data.js`, `dist/components.js`, `dist/app.js`. Every `page-*.js` bundle (plus `videos-data.js`, `itineraries-data.js`, and the `intent-data.js` / `dist/intent.js` pair) loads on demand via `PAGE_MODULES`/`ensureRoute` in `app.jsx`: the active route's bundle before first render, the rest prefetched on first user interaction. **Adding a page means registering it in `PAGE_MODULES` (app.jsx), not adding a `<script>` tag to index.html.** Injected scripts reuse the shared `?v=` (read from the app.js tag), so the cache-buster discipline is unchanged. Only two font families load (EB Garamond + Inter), and since September 2026 they are self-hosted: the variable latin woff2 files under `/fonts` (the same files the PWA ships), declared by `@font-face` at the top of `styles.css`, the two first-screen faces preloaded from `index.html` and the archive template. The former fonts.googleapis.com stylesheet was a render-blocking third-party request on every route. Don't reintroduce it or a third family; `/fonts/*` is served immutable, so a re-cut file needs a new filename.
- **Monetization pass (July 2026, MONETIZATION-IDEAS.md).** New evergreen routes: `/firefall`, `/tioga-opening`, `/half-dome-lottery` (event decision-aid pages — no year in URL or copy; each links its dated deep-dive article, which links back), `/consult` (paid trip consults; the two placeholder consts at the top of `page-consult.jsx` take the owner's Stripe Payment Link + booking URL, mailto CTA until then), `/widget` (embed pitch page). Lodging/camping affiliate networks (MONETIZATION-IDEAS.md 3.1): `affiliate.js` registers `expedia` (LIVE — the Expedia Group Travel Creator camref, Partnerize `prf.hn` wrapper; this is what the article lodging links use), plus `booking`, `stay22`, and `hipcamp` with empty ID consts that fail soft to plain outbound links until approved IDs are pasted in — mirror any ID change in `scripts/gen-prerender.mjs`, which duplicates the builders for prerendered fragments. The money articles (where-to-stay, gateway-towns, camping, trip-cost, plus the kids and pets pieces) carry disclosed availability links through the shared `AvailabilityLink` / `LodgingCta` components + `AffiliateNote` (the placement, disclosure and markup rules are the next bullet); the guardrail (best recommendation stays top, linkless, if unaffiliated) is published on `/affiliate`. The August 2026 optimization pass on top: (1) placement-level GA4 `aff_list` values — `article_cta` / `article_inline` / `article_town` / `trip_selector` / `stay_banner` plus the page-level names, full inventory in ARCHITECTURE.md — so never reuse the retired bare `article`; (2) `LodgingCta` has an optional `image`/`caption`/`credit` figure slot (photo must show the place the link searches; markup mirrored by hand in `gen-prerender.mjs`); (3) `buildTripPlan` returns a `lodging` field (only when the stay answer is `undecided`/`gateway`) that intent.jsx renders through `LodgingCta`, asserted across all 18,200 combinations by `check-intent-tags.mjs`; (4) `ExpediaBanner` (components.jsx) renders Expedia's licensed banner creative from the fail-soft `window.EXPEDIA_BANNER` consts in `affiliate.js` — one placement on `/stay` only, plain `<img>`+`<a>`, never a script/iframe (CSP), and not in the prerender sandbox. Shared `/map?trip=` links get per-trip OG cards: `scripts/gen-og-cards.mjs` pre-generates `img/og/trip-{1..20}.jpg`, `gen-seo-artifacts.mjs` emits the `trip-points.json` `{id: name}` mirror, and `edge/seo.js` overrides title/description/og:image (canonical stays `/map`; `ogUrl` carries the shared URL). `edge/seo.js` also has a `REDIRECTS` table (301s, checked before `seoForPath`) — empty until a slug is retired.
- **Affiliate links: where they go, how they are marked, how they are disclosed (September 2026 revenue pass).** Seven rules, enforced by `scripts/check-affiliate-links.mjs` (in `run check`) wherever a script can see them. (1) **Disclose before the first link, and again beside it.** An article whose body carries any affiliate markup sets `aff: true` on its `window.ARTICLES` entry, and `page-article.jsx` renders the shared `AffiliateDisclosure` line under the byline, above the body, so the reader meets the disclosure before the first link; the end-of-body `AffiliateNote` stays, and every boxed unit (`LodgingCta`, `RecommendedCard`) carries its own one-line disclosure. Standing pages with affiliate links pass `AffiliateDisclosure` into `HpPageHead`'s children (or carry an equivalent line at the top, as `/stay` and `/kit` do). The check fails on a body with affiliate markup and no flag, a flag with no markup, or a flagged body without `AffiliateNote`. (2) **One markup for every affiliate anchor:** `target="_blank"`, `rel="sponsored noopener"`, and `data-aff-network` / `data-aff-list` / `data-aff-item-slug` / `data-aff-name` for the GA4 listener. `noreferrer` is deliberately absent: it hid the referring origin from Impact and Partnerize, which report and validate clicks by it, and the site-wide `Referrer-Policy: strict-origin-when-cross-origin` in `_headers` already trims the referrer to the bare origin, so nothing about the page path leaks. Mint links through `AffLink`, `AvailabilityLink`, `LodgingCta` or `RecommendedCard` (components.jsx, all mirrored in `gen-prerender.mjs`) rather than hand-writing the anchor. (3) **An affiliate link is not an ask.** "One ask per page" and "nothing is asked for twice" govern the Sunday letter, the Field Guide and the consult; a disclosed link attached to advice the page already gives (bring a rain shell, sleep in Mariposa) is editorial and sits outside that count. The budget instead: at most one boxed affiliate unit per section and roughly six affiliate links per article, no pop-ups, no interstitials, and no banner beyond `/stay`'s one `ExpediaBanner`. (4) **Patagonia links go wherever the copy already tells the reader to carry the item** (trail articles, the seasonal kit on `/conditions`, the checklists), not only the gear articles, and they search a *category* (`/search/?q=rain+jacket`) unless the site already names the product, because `/affiliate` promises that every piece of named gear has fifty miles on it. (5) **No stand-in links.** A recommended item that no joined program carries renders linkless (`aff: "#"` in the kit, no `q` in a `RecommendedCard` item); a link to a program that sells something else is worse than none. Networks the site should join are TODO entries at the foot of `affiliate.js`. (6) **Never invent, guess or borrow an affiliate ID, camref or tracking base.** They come only from the owner's network dashboards; an empty const fails soft to a plain outbound link. (7) The guardrail on `/affiliate` outranks all of the above: no program's catalog shapes a recommendation. Every new `aff_list` value is inventoried in ARCHITECTURE.md.
- **Internal links are the site's weakest structural signal, and there is now a system for them (August 2026 SEO pass).** Search Console counted 1,557 internal links reaching 33 pages, only five of which were articles: 66 articles received no contextual inbound link at all. Two causes, both fixed. The related rail picked same-section articles in catalog order filtered by read history, so a crawler (which has no read history) resolved every article in a section to the same three links; and article bodies loaded on a second hop after the page bundle, so the rendered DOM Google measured may never have contained the body or its links. **`window.RELATED` in data.js** now curates 4 to 6 onward links per article by topic, with `relatedFor(slug)` falling back to a rotation that starts at the article's own position in its section (a "first N of the section" fallback recreates the funnel). One table feeds three surfaces that must never disagree: the reader's rail, the "Related reading" block `edge/seo.js` appends **inside** `#prerender-prose` (a sibling would flash, since app.jsx removes exactly that node at boot), and the `related` field in `articles.json`, which the generator resolves by calling `relatedFor` through the catalog harvest rather than reimplementing it. `ensureRoute` in app.jsx preloads the body alongside the route bundle so the first React commit contains it. **Every new article ships 3 to 5 in-body contextual links with descriptive anchor text, woven into sentences that already made the point, plus a `RELATED` entry** (or a deliberate reliance on the fallback). `gen-seo-artifacts.mjs` validates the table and `check-edge-redirects.mjs` asserts every rendered block resolves and that the graph reaches every article.
- **Article section anchors are positional, and Google deep-links them.** `page-article.jsx` assigns `sec-<h2 index>-<slug40>` ids at runtime, only when a heading has no `id` of its own. Inserting, deleting or reordering an `<h2>` therefore renumbers every anchor below it and silently breaks any existing SERP jump link. The gateway-towns piece earns 1,902 impressions across six `#sec-` URLs, so its ten headings now carry hand-authored ids matching what the generator produced; the bears guide's Myth 1 heading does too, because a cross-link points at it. **Before restructuring a long article that ranks, pin its current ids first** — authored ids win, and they also flow into the prerendered fragment, where section anchors otherwise do not exist at all. Until October 2026 a deep link opened at the top of the article on a direct load, because the browser's own hash scroll fires before the lazy-loaded body exists; `page-article.jsx` now scrolls to the fragment two frames after the body is ready (after the sec- ids are assigned), which is also what makes a cross-link into a subsection (the bears guide's `#spring-bears-hungriest`, where the retired spring-bears article now lives) land.
- **Cache-buster discipline.** When you edit a JSX file or `styles.css`, bump its `?v=N` query in `index.html`. Cloudflare and browsers both cache aggressively otherwise. All page scripts and the stylesheet share one version number; bump them together to a new shared number when shipping a batch. `points.geojson` has its **own** `?v=` counter: `window.POINTS_URL` in `itineraries-data.js` (loaded eagerly by both `/map` and `/itineraries`; it used to live in `page-map.jsx`, which a direct load of `/itineraries` never fetched, so that page fell back to the unversioned URL) — bump it separately when editing pins. **Two guards, and they answer different questions.** `bash scripts/check-cache-busters.sh` asks whether a `?v=` is *present* (and whether `window.BODY_VERSIONS` matches `bodies/`); `node scripts/check-asset-freshness.mjs` asks whether it is still *true*. The second one exists because the first one passes a probe that appends a comment to `styles.css` and bumps nothing (CODE-AUDIT-2026-08 §4): it hashes the bytes of all 105 versioned assets against `scripts/data/asset-versions.json`, so a change that ships behind a stale number fails the build instead of sitting invisible behind the CDN. It covers what nothing else could see: every `PAGE_MODULES` bundle (injected with the shared number, which no file mentions), every `dist/bodies/*.js` against its `BODY_VERSIONS` entry, `points.geojson`, `bulletin.json` (including that both readers agree: `BULLETIN_URL` in page-now.jsx and `TIOGA_BULLETIN_URL` in page-tioga-opening.jsx; the homepage stopped reading it in September 2026), and the `/img/` mark and favicon counter. The workflow is bump, then `npm --prefix scripts run assets:stamp`, then commit the regenerated manifest; **`--stamp` refuses to record new bytes under an unchanged version**, because a stamp that could launder a stale number would leave you with the guard you already had.
- **Globals via `window`.** Each JSX file attaches its top-level component to `window` (e.g. `window.GuidePage = GuidePage`) so siblings can reference it. The list of `/* global */` comments at the top of each file declares what it consumes. The full `window.*` API surface, the GA4 event inventory, and the localStorage key inventory are documented in `ARCHITECTURE.md`. All localStorage access goes through `window.safeStorage` (storage.js), never `window.localStorage` directly.
- **Article bodies** live in `bodies/*.jsx` and are **lazy-loaded**, not registered as `<script>` tags in `index.html`. `data.js` indexes each article in `window.ARTICLES` and versions each body per-slug in `window.BODY_VERSIONS`; `window.loadArticleBody(slug)` injects the script on demand. When you add or edit a body, add/bump its `BODY_VERSIONS` entry.
- **`/sitemap.xml` is a sitemap index, not a url set (August 2026).** It points at `/sitemap-articles.xml` (the editorial set, which is what `buildSitemap` writes) and `/archive/sitemap.xml`. Only the editorial one had ever been submitted to Search Console, so the archive got no per-sitemap indexing report and its indexation problem stayed invisible while 139 of its pages sat unindexed. **Anything that parses the sitemap must read the child, not the index**: the index's only `<loc>`s are the two child sitemaps, so a `<loc>` regex over it returns two URLs instead of ninety-odd. `.github/workflows/indexnow.yml` reads `sitemap-articles.xml` for exactly that reason. The archive sitemap also stopped publishing 1922-1954 issue dates as `<lastmod>`; that value is `ARCHIVE_CONTENT_UPDATED` in `gen-archive.mjs`, bumped by hand when a rebuild changes what those pages say, and it cannot derive from the clock because `--check` byte-compares the output.
- **SEO mirrors are generated, not hand-edited.** `data.js` (`window.ARTICLES`) is the single source of truth for the catalog; SEO enrichment the browser does not need (keywords, wordCount, FAQ, trail facts) lives in `seo-data.json` keyed by slug. `articles.json` (imported by the edge Worker `edge/seo.js` at deploy time), `sitemap.xml`, `feed.xml`, the article list in `llms.txt`, and `llms-full.txt` (the full body text of every article in one plain-text file for AI assistants, built from the committed `prerender/` fragments — so refresh prerender before seo when bodies change) are all generated by `scripts/gen-seo-artifacts.mjs`. After adding or editing an article (data.js + its body) and any enrichment (seo-data.json), run `npm --prefix scripts run seo`, then commit the regenerated files. Run `npm --prefix scripts run seo:check` (or `bash scripts/check-seo-artifacts.sh`) before committing — it fails if any mirror is stale. FAQ answers and trail numbers in `seo-data.json` must come from the article's published body; do not invent facts.
- **Responsive images.** `scripts/gen-responsive-images.mjs` writes AVIF/WebP/JPEG variants at several widths into sibling `responsive/` folders (under `img/` and `apps/guide/public/photos/`), slug-named so the in-browser `ResponsiveImage` helper derives URLs with no manifest. Run `npm --prefix scripts run images` after adding source JPEGs.
- **Polish systems (September 2026 pass).** Five small mechanisms, all fixed overlays or a class toggled on an element that already exists, so none of them moves the page. (1) `markNavPending` in app.jsx sets `data-nav-pending` on `<html>` when a route bundle has not arrived within 150ms and `.navprogress` sweeps until it does; a warm session never shows it. (2) `BodySkeleton` in page-article.jsx replaces the italic "Loading…" with paragraph-shaped lines. ## Brand & voice

**Maps start from the official NPS map, never a drawing (owner's rule, September 2026).** Any map of the park on the editorial site, in a mockup, an email or a graphic is built on the National Park Service's official Yosemite map (public domain): `img/nps-yosemite-park-map.jpg` for the park, `img/nps-yosemite-valley-map.jpg` for the Valley. Crop or zoom it to the area the page is about, then add markers, labels and road highlights as a layer on top, and credit "Map: National Park Service". Do not hand-draw a schematic or diagram of the park's geography. The shared pattern is `.npsmap` in `styles.css` (a crop, an SVG in the crop's own pixel space, numbered pins, the caption as the key); the crops are `img/nps-firefall-valley-map.jpg`, `img/nps-mariposa-grove-map.jpg`, `img/nps-el-capitan-map.jpg` and `img/nps-yosemite-four-corners-map.jpg`, and the gateway-towns article overlays the whole park map (`/stay` has its own crop, `img/nps-yosemite-stay-map.jpg`). Bar charts of published figures are data charts, not maps, and are not covered. The Field Guide's own 3D map is a product in its own right and not covered by this rule. `/map` is **not** covered (owner's call, September 30, 2026): the trip builder runs on Google's terrain basemap, as it did before PR #492, because a topographic map at street-level zoom is what a reader building a trip needs, and the NPS overlay capped zoom at 13. `/tioga-opening`, the YARTS article and the gateway-towns article use crops or the whole of the same map.

The brand is **The Talus Field** (formerly "Yosemite Sentinel"). The editorial voice is dry, declarative, journalistic — no marketing fluff, no exclamation marks. House style replaces em-dashes in reader-facing copy with commas, colons, or periods; a deliberate sweep removed them from article bodies, so don't reintroduce them when writing copy. Match the existing tone.

## Things that have surprised past edits

- **A nightly system-checks failure where only the newest articles 404 live means production is running a stale Worker build, not that the repo broke.** Seen Aug 9, 2026: the nightly failed with 404s on exactly the nine articles added in PRs #284–#287 while every mirror-freshness check passed and older articles served fine. `edge/seo.js` imports `articles.json` (and the other JSON catalogs) at deploy time, so the article catalog is frozen into the Worker bundle; a Cloudflare-side rollback or stale build leaves new article URLs 404ing even though the deployed sitemap lists them. Diagnose by checking whether the 404 set aligns with a merge date; fix by redeploying current `main` (any merge to `main` triggers the Workers Build, or retry the latest build in the Cloudflare dashboard). Do not "fix" the repo — it was never wrong. **It recurred Aug 12–14, 2026** with the identical nine-article signature after the #291 redeploy had the nightly green on Aug 10–11: the only pushes between the green Aug 11 run and the red Aug 12 run were the nightly `[skip ci]` Lighthouse chore commits, so production regressed with no merge on this side. A repo-side merge re-triggers the build and clears the symptom, but it cannot prevent the next regression — when this fires again, check the Workers Build deploy history in the Cloudflare dashboard for what rolled the active version back (and consider raising it with Cloudflare support if the history shows no human action). **Since September 2026 the site can answer which build it is running.** `edge/seo.js` serves `/.well-known/talus-build.json` (the slugs frozen into the live bundle, the bulletin edition stamp, and the Worker version from the `version_metadata` binding in `wrangler.jsonc`); `scripts/checks/deploy-parity.mjs` (in the nightly `--online` battery, `npm --prefix scripts run parity:check` by hand) compares that against the live `/articles.json` and the repo and **errors** on exactly the Aug signature, naming the slugs; and `scripts/deploy-parity-log.mjs` writes one record a night to `scripts/data/deploy-parity-log.json` (verdict, version id and timestamp, the three catalog counts) in the same commit as the Lighthouse history, so a rollback reads as a version id changing on a night with no merge. Read the log before the dashboard. Two things to know: the nightly chore commit itself re-triggers the Workers Build (confirmed September 19, 2026: the Worker's modified time matched that commit), so a new version id most nights is expected and the standing question the log answers is whether the *catalog* moved backwards; and the route ships in the same deploy as the check, so the check only warns on a 404 until the log has once recorded a live version, after which a 404 is an error (a build older than the route is serving).
- **PRs here get merged fast, sometimes while a session is still pushing.** PR #219 was merged within a minute of creation; a follow-up commit pushed to the branch afterwards sat stranded on the closed PR and never deployed. Before pushing more commits to a branch that already has a PR, check the PR's state first. If it is merged: rebase the new commits onto `origin/main`, force-with-lease push, and say plainly that a **new** PR is required to ship them — never assume a push to an existing branch will deploy. `.github/workflows/stranded-commits.yml` backstops this: it fails the push and comments on the merged PR when it detects the pattern.
- **The prerendered fragments are downloaded by browsers, not only read by crawlers (September 2026).** `edge/seo.js` injects `/prerender/<slug>.html` into `#root` ahead of the SPA, so every `<img>` in a fragment is fetched on the critical path and discarded when `app.jsx` removes `#prerender-prose`. The stubs in `gen-prerender.mjs` used to emit `<img src="/img/<master>.jpg">`, the un-resized source photo (4 to 9 MB for several articles), and React 19's static renderer hoists a `<link rel="preload">` for every eager `<img>`, so those masters were requested at high priority ahead of the scripts React needs: 43 MB across the catalog, 13 MB on one article, none of it ever shown. The stubs now mirror `ResponsiveImage` exactly (the `<picture>` with AVIF, WebP and JPEG `w`-descriptor sets, `loading="lazy"`), which closes both holes at once: browsers never fetch `src` when a `w` srcset is present, and React hoists no preload for a lazy image or one inside `<picture>`. Two rules follow. A body plate is never the article hero (`page-article.jsx` renders that and the Worker preloads its AVIF), so everything in a fragment stays lazy; and the stubs keep the live component's `sizes` values, because for the first second a fragment's image markup is what the browser paints, not a crawler courtesy.
- **The homepage's LCP element was text in July 2026 and is the shell's hero image since the August redesign; and the nightly Lighthouse LCP is a simulation, not a paint time.** July 2026, throttled phone: the `.hero__dek` paragraph, which is why the head preload of the hero was removed from `index.html` (it fired on every route). September 2026, re-measured with a `PerformanceObserver` in headless Chrome: the only LCP candidate is the static shell's hero `<img>`, painted about 30 ms after FCP (1.6 s on the throttled profile), and React's re-render of the same markup emits no new candidate. The nightly trend nevertheless read 6 to 9 s, because Lighthouse's default mode simulates LCP from a dependency graph rather than reading Chrome's paint: every non-low-priority request that finished before the observed LCP counts, and the graph's biggest node was the 567 KB masthead PNG, requested on every page (see the brand-mark bullet). Shrinking it took the simulated homepage LCP from 6.2 s to about 3.2 s with the observed paint unchanged. Two lessons: read `observedLargestContentfulPaint` in the Lighthouse JSON before trusting the headline number, and remember that a resource never drawn at its downloaded size still sits on the LCP graph if it is fetched at High or Medium priority. The September 2026 visitor-first redesign kept the shape: the same Valley View photo is still the shell's eager, `fetchpriority="high"` hero `<img>`, now inside `.hp-hero figure`, and it is still the only LCP candidate.
- **Chrome's script priority depends on whether an image precedes the script in the body, and the shell scripts are `defer` so that it does not (September 2026).** Chrome fetches a plain parser-blocking `<script>` at High, unless an eager `<img>` came before it in `<body>`, in which case it drops to Medium (the "late body script" rule). The homepage got Medium from the shell's hero; article pages got it by accident, from a full-size master JPEG in the prerendered prose, and lost it the moment that image became lazy: the eight shell scripts jumped to High, ahead of the fonts and hero AVIF, and Lighthouse counted 150 KB of JavaScript as render-blocking (article FCP 1.1 s to 2.0 s in the simulation). The eight `<script>` tags at the end of `index.html` are now `defer`, which makes the order explicit on every route (CSS, fonts and hero first; React after) and changes nothing about when they run, since they already sat at the end of the document and still execute in order. Any new eager shell script goes in that block with `defer`; `PAGE_MODULES` bundles are injected by `app.jsx` and unaffected.
