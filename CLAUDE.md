# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project shape

This repo contains three subsystems for **The Talus Field**, a Yosemite editorial site and field guide product. They are intentionally co-located so a single change (e.g. brand rename, copy update) can touch all three at once.

| Path | What it is | Stack |
|---|---|---|
| repo root (`*.jsx`, `index.html`, `styles.css`, `bodies/`, `img/`) | **Editorial site** at `thetalusfieldjournal.com`: articles, interactive trip-planner map (`/map`), film archive (`/films`), packing checklists. Static, no bundler. | Vanilla React: `*.jsx` sources precompiled into `/dist/*.js` by `scripts/gen-compiled.mjs` (`index.html` loads the dist files); styled with hand-written CSS in `styles.css`. Edge SEO via the root Worker entry `edge/seo.js` (see `wrangler.jsonc`); response headers/CSP in `_headers`. |
| `apps/guide/` | **Field Guide PWA** at `guide.thetalusfieldjournal.com` (custom domain attached at launch; the `talus-field-guide.pages.dev` host keeps resolving alongside it for magic links already sent). Account-gated **paid product** ($3.99 one-time, 18-month access; see "paid model" below), offline-capable. | Vite + React 19 + TypeScript + react-router-dom + zod. |
| `workers/` | **API** at `api.thetalusfieldjournal.com`. Auth, Stripe checkout/webhook, KV-backed buyer records, contact form, IndexNow, NPS programs feed (`/api/programs` + daily cron), live park feeds (`/api/weather`, `/api/waits`, `/api/parking`, `/api/alerts` with the nightly road watch, `/api/air`, `/api/flow`), trip-link email (`/api/trip/email`), PWA trip sync and web push, the remote photo upload (`/photos`). | Cloudflare Worker + Hono + `@tsndr/cloudflare-worker-jwt` + KV. |

Each subsystem carries its own memory file, loaded when you work under it: `apps/guide/CLAUDE.md` (PWA architecture) and `workers/CLAUDE.md` (API routes and auth).

**`ROUTINES.md` is the owner's manual for the scheduled agent fleet** (sixteen Routines as of September 2026: the two weekly articles and the monthly edition, the evergreen refresh, the bulletin turn, the intel cycle and executor, the revenue pulse, the Field Guide depth pass, the Sunday letter draft, the site sweep, and, added September 23, the Field Guide fact audit, the reference page refresh, the season pre-flight, the dependency and security check, and the daily road alert drafter). Each has a runbook under `.claude/skills/<name>/SKILL.md`, and the territory table in ROUTINES.md decides which routine may touch which file; a new routine gets a row there before it gets a cron. The same file records the environment's network access (full Internet since September 2026) and the hosts the runbooks reach.

DEPLOY.md has a full deployment runbook (its "2026 relaunch: enabling the $3.99 paid model" section is the 8-step go-live sequence). It matches the region-based PWA (`valley`/`glacier-mariposa`/`tuolumne`/`hetch-hetchy`, 66 stops, 43 core and 23 hidden, as of September 2026) since the July 2026 launch-prep refresh; if a step contradicts the code, trust the code and fix the doc. `CONVERSION-STRATEGY.md` (July 2026) is the current reader→subscriber→buyer growth plan, successor to `GROWTH-AUDIT.md`. `FEATURE-RESEARCH-2026-09.md` (September 2026) is the cross-product feature determination: five ranked changes for the site and the PWA with market evidence, the price decision that precedes them, and the ideas set aside; its PWA-only companion is `apps/guide/PWA-FEATURE-RESEARCH-2026-09.md`.

## Common commands

Local dev: `.claude/launch.json` has the site + PWA configs; the Worker is `cd workers && npm run dev`.
Tooling scripts live in `scripts/package.json` (`npm --prefix scripts run <script>`); `npm --prefix scripts run check` is the pre-commit gate and `run checks` is the offline health battery.

Dev tooling lives in `scripts/` with its own `package.json`, deliberately not at the repo root, so the root stays a static, build-free deploy. Run `cd scripts && npm install` once before using the npm scripts above. The root `package.json` is NOT a tooling home: it exists only because the Cloudflare Workers Build for the editorial worker runs `npm run build` before deploying, and its `build` script is a no-op echo. Do not add dependencies or real build steps to it (`.assetsignore` also excludes it from the asset upload).

Deployment is **not** done from this repo's CI. On merge to `main`: the **editorial site** deploys via a git-connected Cloudflare **Workers Build** (root `wrangler.jsonc`; it runs the root `npm run build` shim then `npx wrangler deploy`, uploading the repo root as static assets with `edge/seo.js` as the Worker entry); the **PWA** deploys via the git-connected Cloudflare **Pages** project `talus-field-guide` (root dir `apps/guide`, build `npm run build`, output `dist`, Node pinned by `apps/guide/.nvmrc`). The **API Worker** has deployed the same way since September 2026, through its own git-connected **Workers Build** on `talus-field-guide-api` (root dir `workers`, build `npm ci && npm run typecheck && npm run test:flow && npm run test:roads`, deploy `npx wrangler deploy -c wrangler.toml`; the full settings table is in DEPLOY.md section 4). Before that it shipped only by a manual `wrangler deploy`, so an older issue, brief or PR body asking the owner for one describes the retired model. Its settings live in the dashboard, not the repo, and four of them are load-bearing. (1) **Merging an `[api]` PR ships checkout, the Stripe webhook and the buyer records**, and `main` is not branch-protected, so CI's red Worker job does not stop a merge. (2) That is why **the build command is the gate**: the same typecheck and test suites run before `wrangler deploy`, and a failure ships nothing and leaves the previous version serving, so the only signs are the build log on the Worker's Deployments tab and the nightly `checks/api.mjs` parity error. (3) **Build watch paths** are `workers/*` and `scripts/data/deadlines.json` (the Worker imports it at build time), so an article merge does not redeploy the API; a new build-time import from outside `workers/` needs its path added there, or its edits will not ship. (4) **Preview builds are off**: this Worker holds the live Stripe key and the buyer records, and a branch's code has no business running beside them before review. An unattended build never sees wrangler's config-drift prompt (it applies `wrangler.toml` as written), which is one more reason the `[[routes]]` custom-domain block must never leave that file. Secrets are still set by hand (`wrangler secret put`) and survive every deploy. A manual deploy is the recovery path, and it runs from a clean worktree of `origin/main`, never a feature branch: wrangler uploads whatever is on disk, so a branch behind `main` rolls production back.

## Editorial site conventions

- **No bundler, but a compile step.** The `*.jsx` files at the root are the source of truth, but the browser loads the precompiled `/dist/*.js` versions (no in-browser Babel). After editing any root or `bodies/` jsx, run `npm --prefix scripts run compile` and commit the regenerated `dist/` files alongside the source; `npm --prefix scripts run check` fails if they drift. Edge SEO head rewriting is done by `edge/seo.js`, the root Worker's fetch handler (ported from the retired Pages Function `functions/_middleware.js`); it also injects crawler prose for hub routes (`HUB_PROSE`) and serves unknown paths as real 404s.
- **Static homepage shell (July 2026 LCP pass, part two).** `/` ships its above-the-fold markup, the homepage masthead plus the hero, as plain HTML inside `index.html`, between the `GENERATED:HOME-SHELL` markers, so it paints on the first byte instead of waiting on the SPA boot. `scripts/gen-home-shell.mjs` (`npm --prefix scripts run home-shell`, guarded by `run check`) renders it from the **real** `Header` (called with `current: "home"`, so since September 2026 what it bakes is `HomeMasthead`, see the homepage bullet) and `HomeHero` components, so it cannot drift from what React draws a moment later; React replaces it on boot and `app.jsx` removes any leftover `#home-shell`. Three rules: (1) `HomeHero` must render without browser APIs on its first pass, since the generator has no DOM; (2) nothing date-derived may be baked in. The September 2026 hero and masthead carry no dated copy at all, so `DATE_SLOTS` is an empty table, but the mechanism stays: a future dated slot in `HomeHero` or `HomeMasthead` is registered there so the generator blanks it to a stable-height placeholder for React to fill, and the visible-text guard (a four-digit year or the current month name) still fails the build on a leak; (3) `/` is served straight off the asset layer and never invokes the Worker (see `wrangler.jsonc`), which is why the shell lives in `index.html` and `edge/seo.js` *strips* it on every other route. The sr-only `#seo-static-h1` moved out of `index.html` into the Worker for the same reason: the homepage has a real `<h1>`. `MUST_CONTAIN` asserts the h1, the intro, the three section links, the homepage masthead, its search box and its Park now menu survived a refactor; edit that list when the hero's copy changes.
- **The homepage: the visitor-first page (September 2026 redesign, PR #410).** The August 2026 broadsheet (edition rule, index, two-column body with a sticky rail) is gone. `/` is now a hand-written landing page for a first-time visitor, all in `page-home.jsx`, and the source of truth for the design system every route now uses (see the next bullet). Top to bottom: `HomeHero` (eyebrow, h1, intro, two anchor buttons to `#home-start-here` and `#field-guide`, the Valley View photo), a **utility strip** (`.hp-utility`: conditions, entry and reservations, getting around), **Start Here** (`#home-start-here`: one featured card plus three rows, the four first-trip articles), the **Field Guide section** (`#field-guide`, `.hp-product`: three benefit lines, two phone captures from `img/guide/screens/`, the `/guide` button with the price), the **Sunday Letter** (`#home-newsletter`: `NewsletterInline` with its new `inputLabel` prop, `location: home_newsletter`, tag `home`), and **the journal** (`.hp-journal-grid`: three hand-picked reads). Nine things are load-bearing. (1) **The masthead is `HomeMasthead` in `components.jsx`, on every route** (see the Navigation bullet for its structure). `Header` is a thin wrapper that returns it, and on `/` it is what the shell generator bakes: a top strip, the brand, the four navigation labels (Plan a trip, Park now, Map, Read), the search box and a "Get the app" button. On `/` two panel links become jumps to the homepage's own sections (`onHome` in `NAV_GROUPS`: Start here to `#home-start-here`, the Sunday Letter to `#home-newsletter`) and the button jumps to `#field-guide`. (2) **The three menu groups of `NAV_GROUPS` (Plan a trip, Park now, Read) bake into the home shell** as panels (hidden until opened), so the generator's year-leak guard covers their copy and a change to any of them needs `run home-shell` (`--check` fails otherwise). The Read panel's Newest column and the Park now panel's live waits read the catalog and the NPS feed at render or on first open, so the shell bakes the first empty and the second as dashes; both are safe only because every panel is closed at first paint. (3) **`HomeLink`** (`components.jsx`) is the page's only anchor component: modified and middle clicks keep native behaviour, a `#` href scrolls to the section and focuses it (the three sections carry `tabIndex={-1}`; smooth unless reduced motion), any other href goes through `go()` (`/articles/<slug>` becomes `a:<slug>`, everything else its route key), and every click fires `cta_click` (or `guide_cta_click` for `/guide`) with `location` and `target`. The locations are `home_navigation`, `home_hero`, `home_content` and `home_newsletter`; `home_index`, `home_dispatch`, `home_rail` and `home_start_here` are retired and listed in ARCHITECTURE.md, never to be reused. (4) **Everything on the page is hand-written, including the numbers.** The Field Guide section is the shared `HpGuideBand`, whose default points (`HP_GUIDE_POINTS` in `components.jsx`) and button print 44 stops, 57 day hikes, 50 Secret Guide entries, $3.99, 18 months and the 30-day guarantee as literal copy on every page that mounts the band, and the four Start Here reads and three journal picks are literal slugs that mirror `window.START_HERE` in `data.js` by hand. Nothing on the page reads the catalog or the API (the old index counts are gone), so a price change or a change to the guide's content means editing `HP_GUIDE_POINTS` and `HpGuideBand`, a re-curated Start Here means editing this file, and no check catches drift in either. (5) **Nothing is asked for twice** still holds: one guide section, one letter unit, and no lodging unit at all (the rail's Expedia link and its `page_home` `aff_list` are retired). (6) **The page is built from the shared design components** (`HpHeading`, `HpRow`, `HpCard`, `HpGuideBand`, `HpLetter`, beside `HomeLink`), and every change to them is diffed against the homepage at 1440, 1024 and 390: it is the reference render for the whole site. (7) The homepage **fetches nothing**: `HomeBulletin` and `HOME_BULLETIN_URL` are gone, so `bulletin.json` has two readers (`page-now.jsx` and `page-tioga-opening.jsx`) and `check-asset-freshness.mjs` checks those two. (8) The **resume band** (`ResumeReading`, the `resume_shown` and `resume_click` events, the only writer of `tfg.read.resume`) and `DeferredSection` are gone. `page-article.jsx` still writes `tfg.read.last` and still honours `tfg.read.resume` if it is ever set, but no surface sets it now. (9) The old `.home-*` CSS (edition rule, index, body, rail) was deleted in the design rollout's cleanup. Two standing rules: copy in the hero and the masthead stays free of years and month names (the shell guard), and every `HomeLink` href is either a route the router knows or the id of a section on this page.
- **The design system, site-wide (September 2026 rollout, `DESIGN-ROLLOUT.md`).** Every route on the editorial site, plus the generated `/archive/` pages, renders in the homepage's system; the page inventory and its status live in `DESIGN-ROLLOUT.md`. Seven things are load-bearing. (1) **One base layout**: app.jsx renders `<Header>` (`HomeMasthead`), then `<main class="hp-design">`, then `<Footer>`, so every page inherits the tokens, the type and the `:where(.hp-design)` element base from `<main>`; the static home shell's `<main>` carries the same class. Both now restate `.hp-wrap`'s box on their `.wrap`; a change to `.hp-wrap`'s widths or breakpoints has to be mirrored in that rule in `styles.css`. (6) **The masthead's slot is not sticky and its height varies with width** (132px desktop, 173px at phone width; from 761px to 879px the nav takes its own row, as on phones, so its labels never wrap), so `/map` measures it (`useMastheadHeight` in page-map.jsx sets `--masthead-h`) instead of hard-coding a height. Past the slot the header becomes the compact bar (Navigation bullet), which is off on `/map`, so that measurement is unchanged. (7) **The archive's chrome is a hand-kept mirror** in `gen-archive.mjs`: `DESIGN_NAV` (HOME_NAV's four labels, each linked to its group's landing page, since the archive loads no JavaScript and the menus cannot open; the search box as a plain GET form to `/search`; no compact bar) and `siteFooter()` (Footer's columns, the section list read from the catalog, and no copyright year, which would fail `--check` every January 1). Change them with `HOME_NAV` and `Footer`, bump `ARCHIVE_CONTENT_UPDATED`, and run `run archive`. To add or rebuild a page: build it from the `Hp*` components (keep every link, ask, tag and tracking location), add a page layer, then run the pixel diff of `/`, `/planning`, `/conditions` and `/guide` before and after.

- **Navigation (July 2026 pass; one masthead since the September 2026 design rollout; the four-word pass, September 2026).** `NAV_GROUPS` in `components.jsx` is the site's map of primary destinations, and its four words are the site's one navigation vocabulary: **Plan a trip / Park now / Map / Read**, in that order in the masthead (`HOME_NAV`), heading the footer's columns, and sectioning `/explore`. Plan a trip, Park now and Read (key `read`) are menus; Map is a plain link; the Field Guide is the masthead's "Get the app" button. A group is `{ key, label, route, cta, blurb, aside, feature, columns }`: `route` is the landing page and the panel's first link, `aside` a small block under the panel's lede (the trip selector, road alerts), `feature` the panel's third track (`NavMapFeature`, `NavWaitsFeature`, which mounts `EntranceWaits variant="menu"` the first time Park now opens so a page view that never opens it never fetches the feed, and `NavNewestFeature`, the three newest entries), and a link is `{ key }` for an SPA route or `{ href }` for a real navigation, optionally with `hash` (a section on its page, scrolled to once the route has drawn: `/conditions#road-alerts`, `/planning#trip-selector`, `/conditions#cond-waits`) or `onHome` (the homepage section it jumps to when the reader is on `/`). **A menu label is a button, not a link**: a click, a tap, Enter or Space opens and pins its panel; a mouse resting on it opens it (hover only for `pointerType: mouse`; a 400ms close delay and a bridge under the label row carry the pointer down); clicking a hover-opened label pins it rather than closing it; ArrowDown moves into the panel; Escape, a press outside the nav or taking a link closes it. The group holding the current page carries a hairline under its label. **The search box** (`MastheadSearch`, `#masthead-search`, above 1000px; below that the nav's Search link stands in) is a combobox over `window.searchCatalog`: the search bundle loads the first time the box takes focus, never at boot, exact matches come first and the nearest-word correction only when they find nothing, an empty box offers four jump links, Enter on a highlighted result opens it and Enter otherwise (or the last row) hands the query to `/search`. **The compact bar**: past the bottom of the masthead's slot the header is fixed to the top as one row (`.is-stuck`), and the slot keeps its height so nothing moves (no CLS). It is **pinned** above 760px (shown whenever the masthead is out of view, with the article's section as a crumb from 1200px) and **headroom** on phones and on `NAV_HEADROOM_ROUTES` (shown on a scroll up only), which is `/stay`, whose booking bar is also fixed to the top and drops beneath the compact bar while it shows. `<html data-nav-mode>` sets the in-page jump offset (`scroll-padding-top` only where pinned) and `<html data-nav-compact>` lowers the reading bar; the bar is off on `/map`. There is still no hamburger and no phone tab row. Everything else (About, Contact, Directory, Advertise, Widget, Group codes, the legal pages) lives in the `Footer` columns and on `/explore`. Constraints on `NAV_GROUPS`: nothing date-derived and nothing computed from the catalog may appear in its copy (the three menus bake into index.html's static home shell, whose generator runs with an empty `window.ARTICLES` and fails the build on a leaked year), and an entry with `href` instead of `key` is a real navigation and must never get a `go()` handler (that is how `/archive/` is linked). Changing a label or a group means changing `HOME_NAV`, the `Footer` headings, `/explore`'s sections, and the archive's `DESIGN_NAV` / `siteFooter()` together, then `run home-shell` and `run archive`. GA4: panel links fire `cta_click` with `home_navigation` / `site_navigation`; the search box fires `nav_search_submit` and `nav_search_pick` with the same locations (ARCHITECTURE.md). **`/explore` is the site index** (`page-explore.jsx`): every reader-facing destination with a line on what it is, counts drawn live from the catalog, linked from the footer, the 404 page, and `/search`. **`KEEP_GOING`** (also `components.jsx`) is the curated onward-links table keyed by route; `app.jsx` mounts `<KeepGoing>` once under `<main>`, so a page ends in three or four deliberate next steps instead of nothing. A route absent from the table renders nothing — articles have their own related rails, and the home and legal pages want no block. Breadcrumbs are on every standing page.
- **Reader intent: the trip selector and the filters (July 2026).** `/planning` and `/articles` were long sequential lists that only worked if the reader recognised which title answered their question. Two files fix that, both loaded only on those two routes (`PAGE_MODULES`), never in the eager shell: **`intent-data.js`** (raw, uncompiled, like `itineraries-data.js`) carries the taxonomy and the logic, and **`intent.jsx`** (`/dist/intent.js`) carries the React. Three fixed facets — `stage` (before booking / dates set / week before / in the park now), `who` (first trip, families, non-hikers, accessible, dogs, backpacking, photography), `topic` (lodging, camping, permits, transportation, food, trails, conditions) — with `window.ARTICLE_INTENT` tagging every article by hand. Selections are **OR within a facet, AND across facets**, mirrored into the URL with `replaceState` so a filtered view is a shareable link, and each chip's count is scoped to the *other* facets so it dims to zero honestly instead of promising results it cannot deliver. On `/planning` an active filter replaces the five curated parts with matches from the **whole** catalog (a reader who filters for camping wants the camping guide whether or not it earned a slot in the curation); on `/articles` the intent bar composes with the existing section chips. **The bar's last row is "Every entry" (September 2026), and it is the only thing on the page that widens rather than narrows.** The Planning Guide is the front door for a reader who does not yet know which article answers their question, and until this it could not show them most of the site: the five parts curate 21 of the 67 entries, a chip can only reach an article carrying that tag (so an article with an empty facet vanishes the moment a chip in that facet comes on), and the one piece declared in `INTENT_NO_TAGS` had no chip that could ever find it. The switch lists the whole catalog with any chips still applied, mirrors as `?all=1`, and is opt-in by prop (`onToggleBrowse`), so `/articles`, which already lists everything under its chips, does not render it. Three rules: it is **not a fourth facet** (it places no constraint, so it stays out of `intentSelectionCount` and sits below the facet rows behind its own rule); `clear` drops it along with the chips, because clearing is the way back to the curated guide, and the trip selector's hand-off leaves it off, because a plan is a narrowing; and its counts are read live from `PLANNING_SERIES` and the catalog rather than written into the copy. `check-intent-tags.mjs` asserts the empty selection returns the whole catalog (a future change making `matchesIntent` require a tag would pass every other check in that file) and that both halves of the wiring are still there, and prints how much of the catalog only this switch can reach. Four things are load-bearing: (1) an empty facet on an article is a legitimate answer, not an omission — the natural-history essays answer no logistics question and a made-up `topic` tag would put one in front of a reader who asked about permits; (2) `window.ARTICLE_MONTHS` is NOT a facet (there are no month chips, because a reader never asks for "articles about February") but it IS part of a selection: a selection may carry a `month`, which `matchesIntent` ANDs on top of the three facets, and the trip selector's `when` answer rides through the hand-off in `plan.intent` so the seasonal exclusion that governs the five reads governs the "show all N entries that fit this trip" list too. **An August 2026 pass fixed the leak where it did not** — a July trip was offered "Yosemite in Winter" — and the same pass extended the table from ten entries to seventeen, adding the road- and season-dependent pieces (Cathedral Lakes, the Four Mile/Panorama loop, both Half Dome pieces, the Mist Trail, the two bloom pieces, Connecting to Traditions, El Cap spectating). The window for a road-dependent entry is every month `TRIP_MONTHS` does not mark that road `closed`; the window for a season-dependent one is quoted from the article's own published body, the same sourcing rule `seo-data.json` follows. The month is the reader's **visit** month, never their reading month, which is why the Half Dome lottery pieces are windowed to the cable season and not to the March application season. Every month's `TRIP_MONTHS.read` anchor must be inside its own month's window or the table would drop the anchor it is protecting, and no month may fall below 60% of the catalog in season (over-tagging is as quiet a failure as under-tagging); (3) `relaxIntent` loosens a selection until it returns between six entries and half the **in-season** archive, because the honest intersection of five answers is usually empty and half the catalog is not a narrowing — stage-only is deliberately not on the ladder, since dropping the traveler to buy a bigger number throws away the reader's strongest signal, and the month is not on it either, because it is the one answer the park itself enforces; (4) `scripts/check-intent-tags.mjs` (in `npm --prefix scripts run check`, `run intent:check` for the verbose form) is the only thing that can catch drift — an article added without a tag entry is simply invisible to every filter, which reads to a visitor as "the site has nothing on that". An article that is meant to carry no tag in **any** facet (the August 2026 pass declared the first one: "So you want to work in Yosemite" answers no trip-planning question, because it is written for someone weighing a season of work rather than a trip) is declared in **`window.INTENT_NO_TAGS`** with its reason and stops warning, so the untagged warning keeps meaning "somebody forgot" instead of standing permanently and hiding the next one; a declaration that stops matching the tags or the catalog is a build error. Note the difference from an empty single facet, which needs no declaration and is the normal case for the natural-history essays — the fix for "the sequoia essay carries no `topic`" is the missing Mariposa Grove logistics article, never a `trails` tag on an essay about bark. It also sweeps all 18,200 trip-selector answer combinations and fails if any produces an empty read list, an itinerary id the itineraries data does not define, a product route that is not real, a read or a hand-off entry that does not apply in the chosen month, or a chip count that disagrees with the result set the click produces.
- **Who the article is for (August 2026).** `buildTripPlan`'s scoring carries two separate defenses against handing a reader a piece written for somebody else, and they are not the same rule. The **subtraction** (a −1 for each `who` tag the reader did not pick) handles the article that matches one traveler type of three: a weaker match, ranked lower. The **exclusion** handles the article whose `who` set misses the reader entirely, which is not a weaker match but the wrong article — "Bringing a Dog to Yosemite" carries lodging, camping and trails, three of the heaviest topic tags, so it could out-score a general piece by six and lose only one for the dog, and it was landing in the plans of backpackers who never mentioned a dog (~1,500 of the 18,200 combinations). Two carve-outs, both load-bearing: an **untagged** `who` is not a miss (the natural-history essays are written for everyone, and reading a blank as "written for somebody else" would drop exactly the pieces that carry no assumption about the reader), and **anchors are exempt**, on the same principle that puts them above the tag range. The test is against the trip's derived `who`, not the raw `party` answer, because `focus: views` and `focus: photos` legitimately add `non-hikers` and `photography` to the traveler profile.
- **The five-question trip selector** sits at the top of `/planning`: when, how many days, where you are staying, who is traveling, what matters most. The plan appears only when all five are answered (a plan built from two answers is a guess wearing a plan's clothes), and it returns a read list, a day plan, and a paid product. Three rules in `buildTripPlan`: it is **deterministic** (no dates, no randomness — same answers in, same plan out); the itinerary is **capped to what the month's roads allow** and says so, because day two of the two-day plan is Glacier Point Road and day three of the three-day plan is Tioga Road, and handing a January visitor a route over closed gates is the exact failure this site exists to prevent; and the **paid product follows the trip, not the sale** — the Field Guide is the default, `/consult` only for the plans with real constraints (four-plus days, access needs, unbooked peak-season dates), and never for a half-day or budget-focused trip. A fourth rule sits in `TRIP_RULES`: **every answer has to contribute something**, and `focus: wildlife` is the case that proves it — the pieces answering "wildlife and natural history" are the natural-history essays, which carry an empty `topic` by design, so no topic tag can reach them and the rule contributed nothing at all until the August 2026 pass gave it `stage: in-park` (the facet those essays do carry, and the honest reading of the answer) plus a second anchor. Anchors are the only route to a topic-less piece, which is why a focus answer whose articles are all essays needs one. Answers persist in `tfg.trip.selector` and mirror to `?when=&days=&stay=&party=&focus=`, with the URL winning on mount so a shared plan link shows the sender's plan. The month table (`TRIP_MONTHS`) records what a month **decides** (`tioga`/`glacier` = `open` | `closed` | `unsettled`), which is what drives the itinerary cap. It used to have a sibling in `page-home.jsx`'s `MONTHS` (what a month is *like*, for the homepage month planner); the August 2026 homepage redesign retired that planner, so `TRIP_MONTHS` is now the only month table in the editorial site and `/planning` is the only place that asks the reader for a month.

- **Site search (`/search`)** is client-side over `window.ARTICLES` plus a hand-maintained list of standing pages in `page-search.jsx` — no index file to fetch, no third-party widget. It searches **titles, deks, and section names, not article bodies**: bodies are lazy-loaded per slug, so a full-text index would mean pulling all of them down or shipping a fourth generated mirror. The page says so rather than letting a body-text miss read as "the article doesn't exist". `?q=` is mirrored with `replaceState`, not `pushState`, so typing doesn't bury the previous page under one history entry per keystroke, and `edge/seo.js` marks the route `noindex, follow` (a results page is thin, duplicative content, and every `?q=` is another near-identical URL) — which is also why it is NOT in the sitemap table in `gen-seo-artifacts.mjs`, only in `STATIC_ROUTES` for link checking.
- **Trip hand-off to the Field Guide.** The map sidebar's "Open this trip in the Field Guide" links to `<app>/trip?import=<ids>`. The two catalogs overlap but are not identical (`points.geojson` was seeded once from the guide's stops, and several editorial pins match a HIKE id rather than a stop id), so `apps/guide/src/trip/importTrip.ts` resolves alias → stop → hike and **reports what it could not bring across rather than guessing** — a wrong turnout is the failure this product exists to avoid. `scripts/check-trip-bridge.mjs` (in `npm --prefix scripts run check`, `run bridge:check` for the per-pin breakdown) is what keeps that promise honest, because nothing else measures the bridge: the only prior guard lived behind `import.meta.env.DEV` inside `importTrip.ts`, a `console.error` in a browser nobody has open, checking stale aliases alone. It fails on an alias whose target no longer resolves (which degrades to "isn't in the guide", reading to a buyer as missing content rather than a broken table) and on an alias keyed on an id the guide already carries (alias lookup runs first, so it would silently redirect a real entry). It **warns**, rather than fails, on a pin with no counterpart and no `EDITORIAL_ONLY_LABELS` entry — a pin the guide does not carry is legitimate, but an undeclared one falls back to its raw id, so the reader is told "the-fen didn't come across" — and on stale rows in either table. It prints the coverage rate (24/31 as of Aug 2026), which is the number nobody had. - **"The Park Bulletin" (`/now`)** is the one-page everything-happening board (it replaced the weekly "This Week in the Park" dispatch in July 2026): the current NPS Yosemite Guide edition condensed into headline tiles, a dated change ledger, a day-by-day program schedule, road/area status, trail status, hours, transit, and phone numbers. Content lives in `bulletin.json`, rewritten once per Guide edition (~every 5 weeks; its `__comment` is the field reference and the workflow), rendered by `page-now.jsx` (`BulletinPage`; own `?v=` counter on `BULLETIN_URL`, shared with `TIOGA_BULLETIN_URL` in `page-tioga-opening.jsx` (the homepage's `HOME_BULLETIN_URL` went with the September 2026 redesign), like the map's `POINTS_URL`), served to non-JS crawlers via the `HUB_PROSE` entry in `edge/seo.js`, and its sitemap lastmod tracks `edition.updated` automatically. **The September 2026 redesign moved the date arithmetic off the reader and into the page.** It used to print the edition the way the Guide prints it: ten alert paragraphs, a program clock whose rows carried their own day codes and date bounds in the title ("from Sep 4", "Su W F"), three prose cards for the rest of the park, and a calendar half of which had already happened. Every answer was on the page and the reader had to work out which ones still applied. Now `headlines` (two to four editor-written tiles) opens the page; `changes` is one dated ledger the page splits at **today in the park** into "Coming up" and "Already closed" (a past `closes`/`ends` row drops into the closed list, a past `hours` row into "Hours changed", a past `opens`/`event` row disappears because the schedule already carries it); `programs` merges the old `valleyDay`, `elsewhere` and `events` into one structured list the reader filters to a single day and area, with the Guide's free, all-ages and accessible marks as filters; `hours` rows carry `closes` / `then` so a row reads as it is today ("Closed", "8 – 9 since Sep 7"). Five things are load-bearing. (1) **Today is the park's day, not the reader's** (`btParkToday`, America/Los_Angeles): a visitor planning from Berlin at breakfast wants Yosemite's date. (2) **Every helper in `page-now.jsx` carries a `bt` / `BT_` prefix.** Page bundles are classic scripts sharing one global scope, and the first build of the redesign named one `shortDate`, which `page-dates.js` also declares; the schedule crashed on the reader's first interaction, when the prefetch landed. A generic top-level name in a page file is a collision waiting for the next page. (3) **`scripts/check-bulletin.mjs` (in `run check`, `run bulletin:check` alone) is the only thing that can see the new failure mode.** A day code of `thu` for `th`, an `until` before its `from`, or a year typo does not break the page, it silently removes rows from it, and a program that never appears reads as "nothing is on". The check proves every row renders at least once inside the edition window, that no edition day and no area tab is empty, that every retired key is gone, and that no em-dash reached reader-facing copy. (4) **The marks are the printed Guide's own symbols**, `access` / `allAges`, read off its Programs page row by row and **true-only** — an unmarked program is one the Guide did not mark, not one it ruled out, which the schedule's note says in as many words. The same two ride the PWA's program feed as `accessible` / `familyFriendly` in `workers/src/data/manual-programs.ts`; re-read both every edition. (5) **Status colour has its own three tokens** (`--bt-open` / `--bt-warn` / `--bt-closed` in `styles.css`): the chips used to draw "open" in `--moss` and "closed" in `--rust`, which were the same iron red in the retired Golden Hour palette, so an open road and a closed trail differed only by fill. **The icon layer (August 2026)** is the page's wayfinding and its rule is unchanged: `BULLETIN_ICONS` in `page-now.jsx` is the registry, the ordered `[pattern, icon]` tables under it resolve a row's mark from its own name, and `styles.css`'s `.bicon` supplies fill, stroke and weight from `currentColor` so the geometry carries no colour and every palette follows. A mark may only restate what the JSON already says (the chips read `tone`, the program marks read the Guide's symbols, an area reads its own name, a headline reads its optional editor-set `icon`), an unmatched name falls through to the neutral `dot` rather than guessing, and a mark that is the only carrier of its meaning gets a label. Icons are drawn to survive 16px: the first pass shipped a trail curve that rendered as a plain slash and a tent that read as the warning triangle beside it, so redraw and look at the page before believing a path. **The fold (August 2026, kept).** Hours, transit, know-before-you-go and the full phone list are standing reference and sit under four `BulletinFold` `<details>`, closed, with the first four `numbers` pinned above them; the fold **hides, it never drops**, so every row stays in the DOM and the crawler prose is unaffected, and a summary's hint is built by `hintFrom` from the rows' own names rather than hand-written copy that could drift. Adding a section means deciding which half it belongs to, and edition-specific is the higher bar: the page earns its length by answering "what is different", not by being complete. It is a standing editorial commitment: carrying a stale edition past its end date without a note is worse than none, which is what `edition.notice` and the automatic ended-edition banner are for.
- **Internal links are the site's weakest structural signal, and there is now a system for them (August 2026 SEO pass).** Search Console counted 1,557 internal links reaching 33 pages, only five of which were articles: 66 articles received no contextual inbound link at all. Two causes, both fixed. The related rail picked same-section articles in catalog order filtered by read history, so a crawler (which has no read history) resolved every article in a section to the same three links; and article bodies loaded on a second hop after the page bundle, so the rendered DOM Google measured may never have contained the body or its links. **`window.RELATED` in data.js** now curates 4 to 6 onward links per article by topic, with `relatedFor(slug)` falling back to a rotation that starts at the article's own position in its section (a "first N of the section" fallback recreates the funnel). One table feeds three surfaces that must never disagree: the reader's rail, the "Related reading" block `edge/seo.js` appends **inside** `#prerender-prose` (a sibling would flash, since app.jsx removes exactly that node at boot), and the `related` field in `articles.json`, which the generator resolves by calling `relatedFor` through the catalog harvest rather than reimplementing it. `ensureRoute` in app.jsx preloads the body alongside the route bundle so the first React commit contains it. **Every new article ships 3 to 5 in-body contextual links with descriptive anchor text, woven into sentences that already made the point, plus a `RELATED` entry** (or a deliberate reliance on the fallback). `gen-seo-artifacts.mjs` validates the table and `check-edge-redirects.mjs` asserts every rendered block resolves and that the graph reaches every article.
- **Article section anchors are positional, and Google deep-links them.** `page-article.jsx` assigns `sec-<h2 index>-<slug40>` ids at runtime, only when a heading has no `id` of its own. Inserting, deleting or reordering an `<h2>` therefore renumbers every anchor below it and silently breaks any existing SERP jump link. The gateway-towns piece earns 1,902 impressions across six `#sec-` URLs, so its ten headings now carry hand-authored ids matching what the generator produced; the bears guide's Myth 1 heading does too, because a cross-link points at it. **Before restructuring a long article that ranks, pin its current ids first** — authored ids win, and they also flow into the prerendered fragment, where section anchors otherwise do not exist at all.
- **Cache-buster discipline.** When you edit a JSX file or `styles.css`, bump its `?v=N` query in `index.html`. Cloudflare and browsers both cache aggressively otherwise. All page scripts and the stylesheet share one version number; bump them together to a new shared number when shipping a batch. `points.geojson` has its **own** `?v=` counter: `window.POINTS_URL` in `itineraries-data.js` (loaded eagerly by both `/map` and `/itineraries`; it used to live in `page-map.jsx`, which a direct load of `/itineraries` never fetched, so that page fell back to the unversioned URL) — bump it separately when editing pins. **Two guards, and they answer different questions.** `bash scripts/check-cache-busters.sh` asks whether a `?v=` is *present* (and whether `window.BODY_VERSIONS` matches `bodies/`); `node scripts/check-asset-freshness.mjs` asks whether it is still *true*. The second one exists because the first one passes a probe that appends a comment to `styles.css` and bumps nothing (CODE-AUDIT-2026-08 §4): it hashes the bytes of all 105 versioned assets against `scripts/data/asset-versions.json`, so a change that ships behind a stale number fails the build instead of sitting invisible behind the CDN. It covers what nothing else could see: every `PAGE_MODULES` bundle (injected with the shared number, which no file mentions), every `dist/bodies/*.js` against its `BODY_VERSIONS` entry, `points.geojson`, `bulletin.json` (including that both readers agree: `BULLETIN_URL` in page-now.jsx and `TIOGA_BULLETIN_URL` in page-tioga-opening.jsx; the homepage stopped reading it in September 2026), and the `/img/` mark and favicon counter. The workflow is bump, then `npm --prefix scripts run assets:stamp`, then commit the regenerated manifest; **`--stamp` refuses to record new bytes under an unchanged version**, because a stamp that could launder a stale number would leave you with the guard you already had.

## Things that have surprised past edits

- **A nightly system-checks failure where only the newest articles 404 live means production is running a stale Worker build, not that the repo broke.** Seen Aug 9, 2026: the nightly failed with 404s on exactly the nine articles added in PRs #284–#287 while every mirror-freshness check passed and older articles served fine. `edge/seo.js` imports `articles.json` (and the other JSON catalogs) at deploy time, so the article catalog is frozen into the Worker bundle; a Cloudflare-side rollback or stale build leaves new article URLs 404ing even though the deployed sitemap lists them. Diagnose by checking whether the 404 set aligns with a merge date; fix by redeploying current `main` (any merge to `main` triggers the Workers Build, or retry the latest build in the Cloudflare dashboard). Do not "fix" the repo — it was never wrong. **It recurred Aug 12–14, 2026** with the identical nine-article signature after the #291 redeploy had the nightly green on Aug 10–11: the only pushes between the green Aug 11 run and the red Aug 12 run were the nightly `[skip ci]` Lighthouse chore commits, so production regressed with no merge on this side. A repo-side merge re-triggers the build and clears the symptom, but it cannot prevent the next regression — when this fires again, check the Workers Build deploy history in the Cloudflare dashboard for what rolled the active version back (and consider raising it with Cloudflare support if the history shows no human action). **Since September 2026 the site can answer which build it is running.** `edge/seo.js` serves `/.well-known/talus-build.json` (the slugs frozen into the live bundle, the bulletin edition stamp, and the Worker version from the `version_metadata` binding in `wrangler.jsonc`); `scripts/checks/deploy-parity.mjs` (in the nightly `--online` battery, `npm --prefix scripts run parity:check` by hand) compares that against the live `/articles.json` and the repo and **errors** on exactly the Aug signature, naming the slugs; and `scripts/deploy-parity-log.mjs` writes one record a night to `scripts/data/deploy-parity-log.json` (verdict, version id and timestamp, the three catalog counts) in the same commit as the Lighthouse history, so a rollback reads as a version id changing on a night with no merge. Read the log before the dashboard. Two things to know: the nightly chore commit itself re-triggers the Workers Build (confirmed September 19, 2026: the Worker's modified time matched that commit), so a new version id most nights is expected and the standing question the log answers is whether the *catalog* moved backwards; and the route ships in the same deploy as the check, so the check only warns on a 404 until the log has once recorded a live version, after which a 404 is an error (a build older than the route is serving).
- **PRs here get merged fast, sometimes while a session is still pushing.** PR #219 was merged within a minute of creation; a follow-up commit pushed to the branch afterwards sat stranded on the closed PR and never deployed. Before pushing more commits to a branch that already has a PR, check the PR's state first. If it is merged: rebase the new commits onto `origin/main`, force-with-lease push, and say plainly that a **new** PR is required to ship them — never assume a push to an existing branch will deploy. `.github/workflows/stranded-commits.yml` backstops this: it fails the push and comments on the merged PR when it detects the pattern.
- **The prerendered fragments are downloaded by browsers, not only read by crawlers (September 2026).** `edge/seo.js` injects `/prerender/<slug>.html` into `#root` ahead of the SPA, so every `<img>` in a fragment is fetched on the critical path and discarded when `app.jsx` removes `#prerender-prose`. The stubs in `gen-prerender.mjs` used to emit `<img src="/img/<master>.jpg">`, the un-resized source photo (4 to 9 MB for several articles), and React 19's static renderer hoists a `<link rel="preload">` for every eager `<img>`, so those masters were requested at high priority ahead of the scripts React needs: 43 MB across the catalog, 13 MB on one article, none of it ever shown. The stubs now mirror `ResponsiveImage` exactly (the `<picture>` with AVIF, WebP and JPEG `w`-descriptor sets, `loading="lazy"`), which closes both holes at once: browsers never fetch `src` when a `w` srcset is present, and React hoists no preload for a lazy image or one inside `<picture>`. Two rules follow. A body plate is never the article hero (`page-article.jsx` renders that and the Worker preloads its AVIF), so everything in a fragment stays lazy; and the stubs keep the live component's `sizes` values, because for the first second a fragment's image markup is what the browser paints, not a crawler courtesy.
- **The homepage's LCP element was text in July 2026 and is the shell's hero image since the August redesign; and the nightly Lighthouse LCP is a simulation, not a paint time.** July 2026, throttled phone: the `.hero__dek` paragraph, which is why the head preload of the hero was removed from `index.html` (it fired on every route). September 2026, re-measured with a `PerformanceObserver` in headless Chrome: the only LCP candidate is the static shell's hero `<img>`, painted about 30 ms after FCP (1.6 s on the throttled profile), and React's re-render of the same markup emits no new candidate.
