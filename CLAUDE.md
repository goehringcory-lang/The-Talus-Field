# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project shape

This repo contains three subsystems for **The Talus Field**, a Yosemite editorial site and field guide product. They are intentionally co-located so a single change (e.g. brand rename, copy update) can touch all three at once.

| Path | What it is | Stack |
|---|---|---|
| repo root (`*.jsx`, `index.html`, `styles.css`, `bodies/`, `img/`) | **Editorial site** at `thetalusfieldjournal.com`: articles, interactive trip-planner map (`/map`), film archive (`/films`), packing checklists. Static, no bundler. | Vanilla React: `*.jsx` sources precompiled into `/dist/*.js` by `scripts/gen-compiled.mjs` (`index.html` loads the dist files); styled with hand-written CSS in `styles.css`. Edge SEO via the root Worker entry `edge/seo.js` (see `wrangler.jsonc`); response headers/CSP in `_headers`. |
| `apps/guide/` | **Field Guide PWA** at `guide.thetalusfieldjournal.com` (custom domain attached at launch; the `talus-field-guide.pages.dev` host keeps resolving alongside it for magic links already sent). Account-gated **paid product** ($3.99 one-time, 18-month access; see "paid model" below), offline-capable. | Vite + React 19 + TypeScript + react-router-dom + zod. |
| `workers/` | **API** at `api.thetalusfieldjournal.com`. Auth, Stripe checkout/webhook, KV-backed buyer records, contact form, IndexNow, NPS programs feed (`/api/programs` + daily cron), NWS weather proxy (`/api/weather`), trip-link email (`/api/trip/email`). | Cloudflare Worker + Hono + `@tsndr/cloudflare-worker-jwt` + KV. |

Each subsystem carries its own memory file, loaded when you work under it: `apps/guide/CLAUDE.md` (PWA architecture) and `workers/CLAUDE.md` (API routes and auth).

**`ROUTINES.md` is the owner's manual for the scheduled agent fleet** (eleven Routines as of September 2026: the two weekly articles and the monthly edition, the evergreen refresh, the bulletin turn, the intel cycle and executor, the revenue pulse, the Field Guide depth pass, the Sunday letter draft, and the site sweep). Each has a runbook under `.claude/skills/<name>/SKILL.md`, and the territory table in ROUTINES.md decides which routine may touch which file; a new routine gets a row there before it gets a cron. The same file records the environment's network access (full Internet since September 2026) and the hosts the runbooks reach.

DEPLOY.md has a full deployment runbook (its "buy box / Field Guide launch checklist" is the current 8-step go-live sequence). Note that DEPLOY.md was written against the older trip-based PWA model (`1day`/`3day`/`5day`, "35 stops"). The PWA was since refactored to region-based (`valley`/`glacier-mariposa`/`tuolumne`/`hetch-hetchy`, ~44 core stops); treat the smoke-test section as directionally correct but stale on specifics. `CONVERSION-STRATEGY.md` (July 2026) is the current reader→subscriber→buyer growth plan, successor to `GROWTH-AUDIT.md`.

## Common commands

Local dev: `.claude/launch.json` has the site + PWA configs; the Worker is `cd workers && npm run dev`.
Tooling scripts live in `scripts/package.json` (`npm --prefix scripts run <script>`); `npm --prefix scripts run check` is the pre-commit gate and `run checks` is the offline health battery.

Dev tooling lives in `scripts/` with its own `package.json`, deliberately not at the repo root, so the root stays a static, build-free deploy. Run `cd scripts && npm install` once before using the npm scripts above. The root `package.json` is NOT a tooling home: it exists only because the Cloudflare Workers Build for the editorial worker runs `npm run build` before deploying, and its `build` script is a no-op echo. Do not add dependencies or real build steps to it (`.assetsignore` also excludes it from the asset upload).

Deployment is **not** done from this repo's CI. On merge to `main`: the **editorial site** deploys via a git-connected Cloudflare **Workers Build** (root `wrangler.jsonc`; it runs the root `npm run build` shim then `npx wrangler deploy`, uploading the repo root as static assets with `edge/seo.js` as the Worker entry); the **PWA** deploys via the git-connected Cloudflare **Pages** project `talus-field-guide` (root dir `apps/guide`, build `npm run build`, output `dist`, Node pinned by `apps/guide/.nvmrc`). The **API Worker** never auto-deploys: it requires a manual `wrangler deploy` from `workers/` (with KV namespace IDs filled into `wrangler.toml` and secrets set via `wrangler secret put`).

## Editorial site conventions

- **No bundler, but a compile step.** The `*.jsx` files at the root are the source of truth, but the browser loads the precompiled `/dist/*.js` versions (no in-browser Babel). After editing any root or `bodies/` jsx, run `npm --prefix scripts run compile` and commit the regenerated `dist/` files alongside the source; `npm --prefix scripts run check` fails if they drift. Edge SEO head rewriting is done by `edge/seo.js`, the root Worker's fetch handler (ported from the retired Pages Function `functions/_middleware.js`); it also injects crawler prose for hub routes (`HUB_PROSE`) and serves unknown paths as real 404s.
- **Static homepage shell (July 2026 LCP pass, part two).** `/` ships its above-the-fold markup — masthead plus hero — as plain HTML inside `index.html`, between the `GENERATED:HOME-SHELL` markers, so it paints on the first byte instead of waiting on the SPA boot. `scripts/gen-home-shell.mjs` (`npm --prefix scripts run home-shell`, guarded by `run check`) renders it from the **real** `Header` and `HomeHero` components, so it cannot drift from what React draws a moment later; React replaces it on boot and `app.jsx` removes any leftover `#home-shell`. Three rules: (1) `HomeHero` must render without browser APIs on its first pass, since the generator has no DOM; (2) nothing date-derived may be baked in — the hero issue label is blanked to a stable-height placeholder and filled by React, and the generator fails loudly if the slot disappears (`DATE_SLOTS`); (3) `/` is served straight off the asset layer and never invokes the Worker (see `wrangler.jsonc`), which is why the shell lives in `index.html` and `edge/seo.js` *strips* it on every other route. The sr-only `#seo-static-h1` moved out of `index.html` into the Worker for the same reason — the homepage now has a real `<h1>`.
- **The homepage: The Front Page (August 2026 redesign).** `/` had grown to eleven stacked sections, asking for the newsletter three times and pitching the Field Guide twice; no screenful said what the site was. It is now a broadsheet in four parts, all in `page-home.jsx`: the **edition rule** (`.home-edition`, inside `HomeHero` so it bakes into the static shell, and the home of the one date-derived slot), the **lede** (h1, dek, exactly two buttons), the **index** (`HomeIndex`: the journal, the map, the bulletin, the archive, with counts read live from the catalog), and one **two-column body** (`.home-body`) whose left column is editorial (Bulletin, Start Here answers, Latest Entries) and whose right column is the **rail** (`HomeRail`): every offer on the page, made once, ordered by commitment — the paid Field Guide, the free Sunday letter, then lodging availability. Five things are load-bearing. (1) **Nothing is asked for twice**: one guide pitch, one newsletter unit, one lodging unit, so adding a second of any of them is the regression this redesign undid. (2) The rail is **sticky** (`align-self: start` is what makes that work in a grid item). (3) At ≤880px the two columns get `display: contents` and every child of both takes an explicit `order`, interleaving the rail's units into the editorial (Bulletin, guide, letter, answers, lodging, entries) — ordering the rail as a block would put three asks ahead of every word of writing, or bury all three under a full page of editorial; an unset `order` is 0 and jumps the queue, so a new child needs a number. (4) The index's counts come from `window.ARTICLES`/`window.CATEGORIES`, which is exactly why that section sits **below** the hero and not inside it: the shell generator renders with an empty catalog and would bake a zero. (5) The archive entry is a **real navigation** (`href="/archive/"`, no `go()`), like every link into the generated archive. The redesign retired the utility row, the month planner (and its `MONTHS` table and `tfg.trip.month` key), the By Section grid, the Go Deeper ladder, the About/editor strip, and the hero's audience links, guide card and capture box; `/kit` and `/consult` lost their homepage slots and now live in the nav, the footer and `/explore`. Latest Entries and Start Here are **text rows, not cards**: the six-card image grid was the most expensive thing on the page. GA4 locations follow (`home_hero`, `home_index`, `home_dispatch`, `home_rail`); the retired ones are listed in ARCHITECTURE.md and must not be reused.
- **Route-level lazy loading (July 2026 LCP pass).** `index.html` eagerly loads only the shared shell: the self-hosted React UMD files under `/vendor`, `storage.js`, `affiliate.js`, `data.js`, `dist/tweaks-panel.js`, `dist/components.js`, `dist/app.js`. Every `page-*.js` bundle (plus `videos-data.js`, `itineraries-data.js`, and the `intent-data.js` / `dist/intent.js` pair) loads on demand via `PAGE_MODULES`/`ensureRoute` in `app.jsx`: the active route's bundle before first render, the rest prefetched on first user interaction. **Adding a page means registering it in `PAGE_MODULES` (app.jsx), not adding a `<script>` tag to index.html.** Injected scripts reuse the shared `?v=` (read from the app.js tag), so the cache-buster discipline is unchanged. Only two font families load (EB Garamond + Inter), and since September 2026 they are self-hosted: the variable latin woff2 files under `/fonts` (the same files the PWA ships), declared by `@font-face` at the top of `styles.css`, the two first-screen faces preloaded from `index.html` and the archive template. The former fonts.googleapis.com stylesheet was a render-blocking third-party request on every route. Don't reintroduce it or a third family; `/fonts/*` is served immutable, so a re-cut file needs a new filename.
- **Monetization pass (July 2026, MONETIZATION-IDEAS.md).** New evergreen routes: `/firefall`, `/tioga-opening`, `/half-dome-lottery` (event decision-aid pages — no year in URL or copy; each links its dated deep-dive article, which links back), `/consult` (paid trip consults; the two placeholder consts at the top of `page-consult.jsx` take the owner's Stripe Payment Link + booking URL, mailto CTA until then), `/widget` (embed pitch page). Lodging/camping affiliate networks (MONETIZATION-IDEAS.md 3.1): `affiliate.js` registers `expedia` (LIVE — the Expedia Group Travel Creator camref, Partnerize `prf.hn` wrapper; this is what the article lodging links use), plus `booking`, `stay22`, and `hipcamp` with empty ID consts that fail soft to plain outbound links until approved IDs are pasted in — mirror any ID change in `scripts/gen-prerender.mjs`, which duplicates the builders for prerendered fragments. The money articles (where-to-stay, gateway-towns, camping, trip-cost, plus the kids and pets pieces) carry disclosed availability links through the shared `AvailabilityLink` / `LodgingCta` components + `AffiliateNote`; the guardrail (best recommendation stays top, linkless, if unaffiliated) is published on `/affiliate`. The August 2026 optimization pass on top: (1) placement-level GA4 `aff_list` values — `article_cta` / `article_inline` / `article_town` / `trip_selector` / `stay_banner` plus the page-level names, full inventory in ARCHITECTURE.md — so never reuse the retired bare `article`; (2) `LodgingCta` has an optional `image`/`caption`/`credit` figure slot (photo must show the place the link searches; markup mirrored by hand in `gen-prerender.mjs`); (3) `buildTripPlan` returns a `lodging` field (only when the stay answer is `undecided`/`gateway`) that intent.jsx renders through `LodgingCta`, asserted across all 18,200 combinations by `check-intent-tags.mjs`; (4) `ExpediaBanner` (components.jsx) renders Expedia's licensed banner creative from the fail-soft `window.EXPEDIA_BANNER` consts in `affiliate.js` — one placement on `/stay` only, plain `<img>`+`<a>`, never a script/iframe (CSP), and not in the prerender sandbox. Shared `/map?trip=` links get per-trip OG cards: `scripts/gen-og-cards.mjs` pre-generates `img/og/trip-{1..20}.jpg`, `gen-seo-artifacts.mjs` emits the `trip-points.json` `{id: name}` mirror, and `edge/seo.js` overrides title/description/og:image (canonical stays `/map`; `ogUrl` carries the shared URL). `edge/seo.js` also has a `REDIRECTS` table (301s, checked before `seoForPath`) — empty until a slug is retired.
- **Navigation (July 2026 pass, simplified in the July 2026 nav-simplification pass).** Two tables in `components.jsx` are the site's map. `NAV_GROUPS` is the masthead bar, now four items: Plan a Trip (mega dropdown) / Conditions (plain link) / Explore Yosemite (mega dropdown, key `read`) / Field Guide (plain link), each dropdown a column set of `{ key | href, label, note }`. `NAV_SECONDARY` is everything that left the bar (About, Newsletter, Films, the `/archive/` href, Directory, Advertise, Widget, Group codes, Contact): it renders in the hamburger's More section and is mirrored by the footer and `/explore`, never the bar. Constraints on both tables: nothing date-derived and nothing computed from the catalog may appear in the copy (the masthead is rendered into index.html's static home shell by `gen-home-shell.mjs`, which runs with an empty `window.ARTICLES` and fails the build on a leaked year), an entry with `href` instead of `key` is a real navigation and must never get a `go()` handler (that is how `/archive/` is linked), and a route belongs to exactly one table. Search is a top-level masthead destination, not a dropdown item, and the hamburger carries a real query box that pushes `/search?q=` before the route commits. **`BottomNav`** (also `components.jsx`, rendered by `Header` so it bakes into the home shell) is the phone-width persistent bottom tab row — Plan (`/planning`) / Now (`/now`) / Map (`/map`) / Read (`/articles`) — shown at the same ≤880px breakpoint where the inline nav collapses; it returns `null` on `/map` and `/guide`, whose bottom edges belong to the map sheet and the buy bar, and `body:has(.bottomnav)` supplies the content clearance. **`/explore` is the site index** (`page-explore.jsx`): every reader-facing destination with a line on what it is, counts drawn live from the catalog, linked from the hamburger, the footer, the 404 page, and `/search`. **`KEEP_GOING`** (also `components.jsx`) is the curated onward-links table keyed by route; `app.jsx` mounts `<KeepGoing>` once under `<main>`, so a page ends in three or four deliberate next steps instead of nothing. A route absent from the table renders nothing — articles have their own related rails, and the home and legal pages want no block. Breadcrumbs are on every standing page.
- **Reader intent: the trip selector and the filters (July 2026).** `/planning` and `/articles` were long sequential lists that only worked if the reader recognised which title answered their question. Two files fix that, both loaded only on those two routes (`PAGE_MODULES`), never in the eager shell: **`intent-data.js`** (raw, uncompiled, like `itineraries-data.js`) carries the taxonomy and the logic, and **`intent.jsx`** (`/dist/intent.js`) carries the React. Three fixed facets — `stage` (before booking / dates set / week before / in the park now), `who` (first trip, families, non-hikers, accessible, dogs, backpacking, photography), `topic` (lodging, camping, permits, transportation, food, trails, conditions) — with `window.ARTICLE_INTENT` tagging every article by hand. Selections are **OR within a facet, AND across facets**, mirrored into the URL with `replaceState` so a filtered view is a shareable link, and each chip's count is scoped to the *other* facets so it dims to zero honestly instead of promising results it cannot deliver. On `/planning` an active filter replaces the five curated parts with matches from the **whole** catalog (a reader who filters for camping wants the camping guide whether or not it earned a slot in the curation); on `/articles` the intent bar composes with the existing section chips. Four things are load-bearing: (1) an empty facet on an article is a legitimate answer, not an omission — the natural-history essays answer no logistics question and a made-up `topic` tag would put one in front of a reader who asked about permits; (2) `window.ARTICLE_MONTHS` is NOT a facet (there are no month chips, because a reader never asks for "articles about February") but it IS part of a selection: a selection may carry a `month`, which `matchesIntent` ANDs on top of the three facets, and the trip selector's `when` answer rides through the hand-off in `plan.intent` so the seasonal exclusion that governs the five reads governs the "show all N entries that fit this trip" list too. **An August 2026 pass fixed the leak where it did not** — a July trip was offered "Yosemite in Winter" — and the same pass extended the table from ten entries to seventeen, adding the road- and season-dependent pieces (Cathedral Lakes, the Four Mile/Panorama loop, both Half Dome pieces, the Mist Trail, the two bloom pieces, Connecting to Traditions, El Cap spectating). The window for a road-dependent entry is every month `TRIP_MONTHS` does not mark that road `closed`; the window for a season-dependent one is quoted from the article's own published body, the same sourcing rule `seo-data.json` follows. The month is the reader's **visit** month, never their reading month, which is why the Half Dome lottery pieces are windowed to the cable season and not to the March application season. Every month's `TRIP_MONTHS.read` anchor must be inside its own month's window or the table would drop the anchor it is protecting, and no month may fall below 60% of the catalog in season (over-tagging is as quiet a failure as under-tagging); (3) `relaxIntent` loosens a selection until it returns between six entries and half the **in-season** archive, because the honest intersection of five answers is usually empty and half the catalog is not a narrowing — stage-only is deliberately not on the ladder, since dropping the traveler to buy a bigger number throws away the reader's strongest signal, and the month is not on it either, because it is the one answer the park itself enforces; (4) `scripts/check-intent-tags.mjs` (in `npm --prefix scripts run check`, `run intent:check` for the verbose form) is the only thing that can catch drift — an article added without a tag entry is simply invisible to every filter, which reads to a visitor as "the site has nothing on that". An article that is meant to carry no tag in **any** facet (the August 2026 pass declared the first one: "So you want to work in Yosemite" answers no trip-planning question, because it is written for someone weighing a season of work rather than a trip) is declared in **`window.INTENT_NO_TAGS`** with its reason and stops warning, so the untagged warning keeps meaning "somebody forgot" instead of standing permanently and hiding the next one; a declaration that stops matching the tags or the catalog is a build error. Note the difference from an empty single facet, which needs no declaration and is the normal case for the natural-history essays — the fix for "the sequoia essay carries no `topic`" is the missing Mariposa Grove logistics article, never a `trails` tag on an essay about bark. It also sweeps all 18,200 trip-selector answer combinations and fails if any produces an empty read list, an itinerary id the itineraries data does not define, a product route that is not real, a read or a hand-off entry that does not apply in the chosen month, or a chip count that disagrees with the result set the click produces.
- **Who the article is for (August 2026).** `buildTripPlan`'s scoring carries two separate defenses against handing a reader a piece written for somebody else, and they are not the same rule. The **subtraction** (a −1 for each `who` tag the reader did not pick) handles the article that matches one traveler type of three: a weaker match, ranked lower. The **exclusion** handles the article whose `who` set misses the reader entirely, which is not a weaker match but the wrong article — "Bringing a Dog to Yosemite" carries lodging, camping and trails, three of the heaviest topic tags, so it could out-score a general piece by six and lose only one for the dog, and it was landing in the plans of backpackers who never mentioned a dog (~1,500 of the 18,200 combinations). Two carve-outs, both load-bearing: an **untagged** `who` is not a miss (the natural-history essays are written for everyone, and reading a blank as "written for somebody else" would drop exactly the pieces that carry no assumption about the reader), and **anchors are exempt**, on the same principle that puts them above the tag range. The test is against the trip's derived `who`, not the raw `party` answer, because `focus: views` and `focus: photos` legitimately add `non-hikers` and `photography` to the traveler profile.
- **The five-question trip selector** sits at the top of `/planning`: when, how many days, where you are staying, who is traveling, what matters most. The plan appears only when all five are answered (a plan built from two answers is a guess wearing a plan's clothes), and it returns a read list, a day plan, and a paid product. Three rules in `buildTripPlan`: it is **deterministic** (no dates, no randomness — same answers in, same plan out); the itinerary is **capped to what the month's roads allow** and says so, because day two of the two-day plan is Glacier Point Road and day three of the three-day plan is Tioga Road, and handing a January visitor a route over closed gates is the exact failure this site exists to prevent; and the **paid product follows the trip, not the sale** — the Field Guide is the default, `/consult` only for the plans with real constraints (four-plus days, access needs, unbooked peak-season dates), and never for a half-day or budget-focused trip. A fourth rule sits in `TRIP_RULES`: **every answer has to contribute something**, and `focus: wildlife` is the case that proves it — the pieces answering "wildlife and natural history" are the natural-history essays, which carry an empty `topic` by design, so no topic tag can reach them and the rule contributed nothing at all until the August 2026 pass gave it `stage: in-park` (the facet those essays do carry, and the honest reading of the answer) plus a second anchor. Anchors are the only route to a topic-less piece, which is why a focus answer whose articles are all essays needs one. Answers persist in `tfg.trip.selector` and mirror to `?when=&days=&stay=&party=&focus=`, with the URL winning on mount so a shared plan link shows the sender's plan. The month table (`TRIP_MONTHS`) records what a month **decides** (`tioga`/`glacier` = `open` | `closed` | `unsettled`), which is what drives the itinerary cap. It used to have a sibling in `page-home.jsx`'s `MONTHS` (what a month is *like*, for the homepage month planner); the August 2026 homepage redesign retired that planner, so `TRIP_MONTHS` is now the only month table in the editorial site and `/planning` is the only place that asks the reader for a month.
- **The Planning Guide's five parts** (`PLANNING_PARTS` in `page-planning-guide.jsx`) own the copy but not the membership: the slugs come from `window.PLANNING_SERIES` in `data.js`, which the article pages already read for their "part of the Planning Guide" series band. One list, so the page and the band cannot disagree about what is in Part Three; the coupling is by exact part label, and `check-intent-tags.mjs` fails if a label stops resolving (it would render a part with no articles under it).
- **Site search (`/search`)** is client-side over `window.ARTICLES` plus a hand-maintained list of standing pages in `page-search.jsx` — no index file to fetch, no third-party widget. It searches **titles, deks, and section names, not article bodies**: bodies are lazy-loaded per slug, so a full-text index would mean pulling all of them down or shipping a fourth generated mirror. The page says so rather than letting a body-text miss read as "the article doesn't exist". `?q=` is mirrored with `replaceState`, not `pushState`, so typing doesn't bury the previous page under one history entry per keystroke, and `edge/seo.js` marks the route `noindex, follow` (a results page is thin, duplicative content, and every `?q=` is another near-identical URL) — which is also why it is NOT in the sitemap table in `gen-seo-artifacts.mjs`, only in `STATIC_ROUTES` for link checking.
- **Trip hand-off to the Field Guide.** The map sidebar's "Open this trip in the Field Guide" links to `<app>/trip?import=<ids>`. The two catalogs overlap but are not identical (`points.geojson` was seeded once from the guide's stops, and several editorial pins match a HIKE id rather than a stop id), so `apps/guide/src/trip/importTrip.ts` resolves alias → stop → hike and **reports what it could not bring across rather than guessing** — a wrong turnout is the failure this product exists to avoid. `scripts/check-trip-bridge.mjs` (in `npm --prefix scripts run check`, `run bridge:check` for the per-pin breakdown) is what keeps that promise honest, because nothing else measures the bridge: the only prior guard lived behind `import.meta.env.DEV` inside `importTrip.ts`, a `console.error` in a browser nobody has open, checking stale aliases alone. It fails on an alias whose target no longer resolves (which degrades to "isn't in the guide", reading to a buyer as missing content rather than a broken table) and on an alias keyed on an id the guide already carries (alias lookup runs first, so it would silently redirect a real entry). It **warns**, rather than fails, on a pin with no counterpart and no `EDITORIAL_ONLY_LABELS` entry — a pin the guide does not carry is legitimate, but an undeclared one falls back to its raw id, so the reader is told "the-fen didn't come across" — and on stale rows in either table. It prints the coverage rate (24/31 as of Aug 2026), which is the number nobody had. Ids are also stashed at PWA boot (`tfg.trip.pendingImport`, 30-day TTL) because a reader who does not own the guide yet leaves for Stripe and returns through `/open?token=`, which knows nothing about the trip; Home then offers it, and only an explicit tap writes to the plan.
- **"The Park Bulletin" (`/now`)** is the one-page everything-happening board (it replaced the weekly "This Week in the Park" dispatch in July 2026): the current NPS Yosemite Guide edition condensed into alerts, road/area status, the free-program clock, dated events (auto-dimmed once past), trail status, hours, transit, and phone numbers. Content lives in `bulletin.json`, rewritten once per Guide edition (~every 5 weeks; see its `__comment` for the workflow), rendered by `page-now.jsx` (`BulletinPage`; own `?v=` counter on `BULLETIN_URL` shared with `HOME_BULLETIN_URL` in `page-home.jsx`, like the map's `POINTS_URL`), served to non-JS crawlers via the `HUB_PROSE` entry in `edge/seo.js`, and its sitemap lastmod tracks `edition.updated` automatically. The Valley clock rows carry optional `access` / `allAges` booleans: these are the printed Guide's own per-program symbols (wheelchair accessible, recommended for families), read off its Programs page row by row and **true-only** — an unmarked program is one the Guide did not mark, not one it ruled out, so nothing renders in the false case and the note says as much. The same two marks ride the PWA's program feed as `accessible` / `familyFriendly` in `workers/src/data/manual-programs.ts`; re-read both from the new Programs page on every edition turn. **The icon layer (August 2026)** is the page's wayfinding: `BULLETIN_ICONS` in `page-now.jsx` is the registry, the ordered `[pattern, icon]` tables under it resolve a row's mark from its own name, and `styles.css`'s `.bicon` supplies fill, stroke and weight from `currentColor` so the geometry carries no colour and all four palettes follow. Three rules hold it up. (1) A mark may only restate what the JSON already says: the status chips read `tone`, the program marks read the Guide's own `access` / `allAges`, an area reads its own name, and an alert reads its optional editor-set `icon` (`{ icon, text }`; a bare string still works, and `edge/seo.js` carries only the text across). Nothing derives a mark from a fact the bulletin does not carry, which is why the trail rows have no per-row mark: a trail has no category field, and eleven identical route marks were decoration that the chips were already doing better. (2) An unmatched name falls through to the neutral `dot`, because this file is rewritten by hand every five weeks and the tables will meet rows they do not know: a missing mark reads as unmarked, which is true, and a wrong one reads as a fact. (3) A mark that is the only carrier of its meaning gets a label, which is the two Guide symbols on the clock and nothing else. Icons are also drawn to survive 16px: the first pass shipped a trail curve that rendered as a plain slash and a tent that read as the warning triangle beside it, so redraw and look at the page before believing a path. **The fold (August 2026 simplification).** The page answers two questions and they are not equally urgent: "what is different this edition" is why a reader opens it, and "what are the hours / how do I get there / what should I know" is standing reference that barely moves between editions but was taking two thirds of the page. The edition-specific half (lede, alerts, roads and areas, the clock, elsewhere, events, trails, now full width) stays open; hours, transit, know-before-you-go and the phone numbers moved into `.bulletin-ref`, four `BulletinFold` `<details>` closed by default. Three things hold it up: (1) the fold **hides, it never drops** — every row stays in the DOM, which is why the `HUB_PROSE` crawler prose in `edge/seo.js` needed no change; (2) a summary's hint follows the same rule as the icons, restating only what the JSON already carries (it is built by `hintFrom` from the rows' own names, joined with middots because several labels contain commas), never hand-written copy that could drift from the data under it; (3) adding a section means deciding which half it belongs to, and edition-specific is the higher bar — the page earns its length by answering "what changed", not by being complete. The same pass cut the alerts band back to headlines: an alert is the read-this-first line and the detail belongs to the section that owns it (the Mist Trail schedule to `trails`, the shuttle dates to `transit`), so nothing was deleted that is not still stated below. It is a standing editorial commitment: carrying a stale edition past its end date without a note is worse than none.
- **Internal links are the site's weakest structural signal, and there is now a system for them (August 2026 SEO pass).** Search Console counted 1,557 internal links reaching 33 pages, only five of which were articles: 66 articles received no contextual inbound link at all. Two causes, both fixed. The related rail picked same-section articles in catalog order filtered by read history, so a crawler (which has no read history) resolved every article in a section to the same three links; and article bodies loaded on a second hop after the page bundle, so the rendered DOM Google measured may never have contained the body or its links. **`window.RELATED` in data.js** now curates 4 to 6 onward links per article by topic, with `relatedFor(slug)` falling back to a rotation that starts at the article's own position in its section (a "first N of the section" fallback recreates the funnel). One table feeds three surfaces that must never disagree: the reader's rail, the "Related reading" block `edge/seo.js` appends **inside** `#prerender-prose` (a sibling would flash, since app.jsx removes exactly that node at boot), and the `related` field in `articles.json`, which the generator resolves by calling `relatedFor` through the catalog harvest rather than reimplementing it. `ensureRoute` in app.jsx preloads the body alongside the route bundle so the first React commit contains it. **Every new article ships 3 to 5 in-body contextual links with descriptive anchor text, woven into sentences that already made the point, plus a `RELATED` entry** (or a deliberate reliance on the fallback). `gen-seo-artifacts.mjs` validates the table and `check-edge-redirects.mjs` asserts every rendered block resolves and that the graph reaches every article.
- **Article section anchors are positional, and Google deep-links them.** `page-article.jsx` assigns `sec-<h2 index>-<slug40>` ids at runtime, only when a heading has no `id` of its own. Inserting, deleting or reordering an `<h2>` therefore renumbers every anchor below it and silently breaks any existing SERP jump link. The gateway-towns piece earns 1,902 impressions across six `#sec-` URLs, so its ten headings now carry hand-authored ids matching what the generator produced; the bears guide's Myth 1 heading does too, because a cross-link points at it. **Before restructuring a long article that ranks, pin its current ids first** — authored ids win, and they also flow into the prerendered fragment, where section anchors otherwise do not exist at all.
- **Cache-buster discipline.** When you edit a JSX file or `styles.css`, bump its `?v=N` query in `index.html`. Cloudflare and browsers both cache aggressively otherwise. All page scripts and the stylesheet share one version number; bump them together to a new shared number when shipping a batch. `points.geojson` has its **own** `?v=` counter: `window.POINTS_URL` in `itineraries-data.js` (loaded eagerly by both `/map` and `/itineraries`; it used to live in `page-map.jsx`, which a direct load of `/itineraries` never fetched, so that page fell back to the unversioned URL) — bump it separately when editing pins. **Two guards, and they answer different questions.** `bash scripts/check-cache-busters.sh` asks whether a `?v=` is *present* (and whether `window.BODY_VERSIONS` matches `bodies/`); `node scripts/check-asset-freshness.mjs` asks whether it is still *true*. The second one exists because the first one passes a probe that appends a comment to `styles.css` and bumps nothing (CODE-AUDIT-2026-08 §4): it hashes the bytes of all 105 versioned assets against `scripts/data/asset-versions.json`, so a change that ships behind a stale number fails the build instead of sitting invisible behind the CDN. It covers what nothing else could see: every `PAGE_MODULES` bundle (injected with the shared number, which no file mentions), every `dist/bodies/*.js` against its `BODY_VERSIONS` entry, `points.geojson`, `bulletin.json` (including that all three readers agree: `BULLETIN_URL` in page-now.jsx, `HOME_BULLETIN_URL` in page-home.jsx, and `TIOGA_BULLETIN_URL` in page-tioga-opening.jsx), and the `/img/` mark and favicon counter. The workflow is bump, then `npm --prefix scripts run assets:stamp`, then commit the regenerated manifest; **`--stamp` refuses to record new bytes under an unchanged version**, because a stamp that could launder a stale number would leave you with the guard you already had.

The list of `/* global */` comments at the top of each file declares what it consumes. ## Things that have surprised past edits

- **A nightly system-checks failure where only the newest articles 404 live means production is running a stale Worker build, not that the repo broke.** Seen Aug 9, 2026: the nightly failed with 404s on exactly the nine articles added in PRs #284–#287 while every mirror-freshness check passed and older articles served fine. `edge/seo.js` imports `articles.json` (and the other JSON catalogs) at deploy time, so the article catalog is frozen into the Worker bundle; a Cloudflare-side rollback or stale build leaves new article URLs 404ing even though the deployed sitemap lists them. Diagnose by checking whether the 404 set aligns with a merge date; fix by redeploying current `main` (any merge to `main` triggers the Workers Build, or retry the latest build in the Cloudflare dashboard). Do not "fix" the repo — it was never wrong. **It recurred Aug 12–14, 2026** with the identical nine-article signature after the #291 redeploy had the nightly green on Aug 10–11: the only pushes between the green Aug 11 run and the red Aug 12 run were the nightly `[skip ci]` Lighthouse chore commits, so production regressed with no merge on this side. A repo-side merge re-triggers the build and clears the symptom, but it cannot prevent the next regression — when this fires again, check the Workers Build deploy history in the Cloudflare dashboard for what rolled the active version back (and consider raising it with Cloudflare support if the history shows no human action).
- **PRs here get merged fast, sometimes while a session is still pushing.** PR #219 was merged within a minute of creation; a follow-up commit pushed to the branch afterwards sat stranded on the closed PR and never deployed. Before pushing more commits to a branch that already has a PR, check the PR's state first. If it is merged: rebase the new commits onto `origin/main`, force-with-lease push, and say plainly that a **new** PR is required to ship them — never assume a push to an existing branch will deploy. `.github/workflows/stranded-commits.yml` backstops this: it fails the push and comments on the merged PR when it detects the pattern.
- **The prerendered fragments are downloaded by browsers, not only read by crawlers (September 2026).** `edge/seo.js` injects `/prerender/<slug>.html` into `#root` ahead of the SPA, so every `<img>` in a fragment is fetched on the critical path and discarded when `app.jsx` removes `#prerender-prose`. The stubs in `gen-prerender.mjs` used to emit `<img src="/img/<master>.jpg">`, the un-resized source photo (4 to 9 MB for several articles), and React 19's static renderer hoists a `<link rel="preload">` for every eager `<img>`, so those masters were requested at high priority ahead of the scripts React needs: 43 MB across the catalog, 13 MB on one article, none of it ever shown. The stubs now mirror `ResponsiveImage` exactly (the `<picture>` with AVIF, WebP and JPEG `w`-descriptor sets, `loading="lazy"`), which closes both holes at once: browsers never fetch `src` when a `w` srcset is present, and React hoists no preload for a lazy image or one inside `<picture>`. Two rules follow. A body plate is never the article hero (`page-article.jsx` renders that and the Worker preloads its AVIF), so everything in a fragment stays lazy; and the stubs keep the live component's `sizes` values, because for the first second a fragment's image markup is what the browser paints, not a crawler courtesy.
- **The homepage's LCP element was text in July 2026 and is the shell's hero image since the August redesign; and the nightly Lighthouse LCP is a simulation, not a paint time.** July 2026, throttled phone: the `.hero__dek` paragraph, which is why the head preload of the hero was removed from `index.html` (it fired on every route). September 2026, re-measured with a `PerformanceObserver` in headless Chrome: the only LCP candidate is the static shell's hero `<img>`, painted about 30 ms after FCP (1.6 s on the throttled profile), and React's re-render of the same markup emits no new candidate. The nightly trend nevertheless read 6 to 9 s, because Lighthouse's default mode simulates LCP from a dependency graph rather than reading Chrome's paint: every non-low-priority request that finished before the observed LCP counts, and the graph's biggest node was the 567 KB masthead PNG, requested on every page (see the brand-mark bullet). Shrinking it took the simulated homepage LCP from 6.2 s to about 3.2 s with the observed paint unchanged. Two lessons: read `observedLargestContentfulPaint` in the Lighthouse JSON before trusting the headline number, and remember that a resource never drawn at its downloaded size still sits on the LCP graph if it is fetched at High or Medium priority.
- **Chrome's script priority depends on whether an image precedes the script in the body, and the shell scripts are `defer` so that it does not (September 2026).** Chrome fetches a plain parser-blocking `<script>` at High, unless an eager `<img>` came before it in `<body>`, in which case it drops to Medium (the "late body script" rule). The homepage got Medium from the shell's hero; article pages got it by accident, from a full-size master JPEG in the prerendered prose, and lost it the moment that image became lazy: the eight shell scripts jumped to High, ahead of the fonts and hero AVIF, and Lighthouse counted 150 KB of JavaScript as render-blocking (article FCP 1.1 s to 2.0 s in the simulation). The eight `<script>` tags at the end of `index.html` are now `defer`, which makes the order explicit on every route (CSS, fonts and hero first; React after) and changes nothing about when they run, since they already sat at the end of the document and still execute in order. Any new eager shell script goes in that block with `defer`; `PAGE_MODULES` bundles are injected by `app.jsx` and unaffected.
