# SEO runbook

Operational notes for keeping thetalusfieldjournal.com indexed and discoverable.
Most of this is manual work in Google Search Console (GSC); the code side is
small and documented at the bottom.

## The actual bottleneck: getting pages crawled and indexed

A new site with low authority gets a small crawl budget. Google reports many
URLs as "Discovered, currently not indexed" (never crawled). Code cannot force
indexing. The levers that work:

1. **Request indexing manually.** GSC, URL Inspection, paste the URL, "Request
   Indexing." Prioritize the articles tied to live impressions:
   - `/articles/where-to-eat-yosemite` (dining/restaurants queries)
   - `/articles/tioga-road-opening-weekend-2026` (Tioga Pass opening queries)
   - `/articles/mist-trail-the-real-guide`
   - `/half-dome-lottery` (the dated article was retired into this page in
     August 2026 and 301s here; do not request indexing on the old slug)
   - `/articles/four-mile-up-panorama-down`
   - plus the hubs: `/`, `/planning`, `/articles`
2. **Earn backlinks.** r/Yosemite, r/nationalparks, hiking forums, blogger
   outreach, and sharing each new article. Backlinks drive both discovery and
   ranking for a young domain.
3. **Time + internal linking.** Internal linking is already in place (see
   "Already handled" below); keep it intact as articles are added.

## Sitemaps: an index and two children

`/sitemap.xml` is a **sitemap index**, not a url set. It lists two children:

- `/sitemap-articles.xml` — the editorial url set (hubs, sections, static pages,
  every article), generated by `scripts/gen-seo-artifacts.mjs`.
- `/archive/sitemap.xml` — the 569 Nature Notes URLs, generated by
  `scripts/gen-archive.mjs`.

Submit **the index** in Search Console. Until August 2026 only the editorial
sitemap was submitted, so the archive got no per-sitemap indexing report and its
indexation problem (139 pages in "Crawled - currently not indexed") was
invisible in the Sitemaps view. An index gives per-child reporting for free.

Anything that parses the sitemap must read the **child**, not the index: the
index's only `<loc>`s are the two child sitemaps, so a `<loc>` regex over it
returns two sitemap URLs rather than every page. `.github/workflows/indexnow.yml`
reads `sitemap-articles.xml` for exactly this reason.

### The "Incorrect namespace" error

Search Console reported this against `/sitemap.xml` from launch until August
2026, and it was real: the image extension namespace was written
`schemas/sitemaps-image/1.1`. Google's is `sitemap-image`, singular. Every
`<image:image>` block in the file was being ignored. Fixed in
`gen-seo-artifacts.mjs`; the comment at the declaration is the only guard, since
`scripts/lib/xml.mjs` checks tag balance and not namespace URIs.

If the error reappears, check **which** submitted file is flagged. `feed.xml` is
an RSS 2.0 feed (root `<rss version="2.0">`), not a sitemap; if it was ever
submitted in the Sitemaps report, GSC validates it as a sitemap and the RSS root
fails that check. Remove it from Sitemaps (it is fine as the site's RSS feed).

## Publishing checklist

The SEO mirrors are generated, not hand-maintained. When you add or edit an
article:

1. Edit `data.js` (`window.ARTICLES` and the `window.BODY_VERSIONS` map) and
   the article body in `bodies/<slug>.jsx`.
2. Add enrichment (seoDek in data.js; wordCount / keywords / faq / trail in
   `seo-data.json`). FAQ answers and trail numbers must come from the
   published body; do not invent facts.
3. Run `npm --prefix scripts run seo` — this regenerates `articles.json`
   (consumed by the edge Worker `edge/seo.js`), `sitemap.xml`, `feed.xml`,
   the llms.txt article list, **and the `<noscript>` article list in
   `index.html`** (between GENERATED markers; what non-JS crawlers read for
   internal links).
4. Run `npm --prefix scripts run prerender` and `npm --prefix scripts run compile`
   to refresh the prerendered prose fragment and the compiled page scripts.
5. If the hero image is new, run `npm --prefix scripts run images`. Sources
   narrower than 1200px automatically get an upscaled
   `img/responsive/<slug>-og.jpg` social card so og:image stays ≥1200px wide.

Then bump the shared `?v=N` cache-buster on the edited files in `index.html`,
run `bash scripts/check-cache-busters.sh` and
`npm --prefix scripts run seo:check` before committing.

## Already handled (do not regress these)

- **Per-route head metadata.** `edge/seo.js` (the root Worker) rewrites title, meta
  description, canonical, Open Graph, Twitter, and JSON-LD per route on the edge,
  so non-JS crawlers get correct metadata from the first byte.
- **Internal linking.** The `<noscript>` block in `index.html` links every
  article; each article page ends with related links; global nav and footer link
  the hubs; every article is within two clicks of the homepage via `/articles`.
- **Single H1 per page.** A screen-reader-only static `<h1>` lives in
  `index.html` for non-JS HTML parsers (Bing's auditor). `app.jsx` removes it on
  boot so JS-rendering crawlers and users see exactly one `<h1>` (the per-route
  title). Keep both halves; removing only one reintroduces a duplicate H1 or
  drops the no-JS fallback.
- **Structured data.** Article, BreadcrumbList, WebSite, and Organization schema
  are emitted; breadcrumbs validate clean.
- **Social cards.** The sitewide default og:image is `img/og-default.jpg`, a
  1200×630 landscape card generated by `scripts/gen-responsive-images.mjs`
  (referenced from index.html, app.jsx, and edge/seo.js — keep the
  three in sync). Per-article og:images resolve through `ogImageFor` in
  `scripts/lib/catalog.mjs`, which falls back to an upscaled
  `<slug>-og.jpg` when the source photo is narrower than 1200px.
- **Prerender fragments are noindexed.** `/prerender/*` carries
  `X-Robots-Tag: noindex` in `_headers` so the raw prose fragments the edge
  middleware injects into article HTML are never indexed as duplicate content.
